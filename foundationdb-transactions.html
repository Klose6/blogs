FoundationDB Distributed Transactions

How FoundationDB atomically transfers $100 across two storage-server shards using a consistent read version, client-side write buffering, optimistic conflict ranges, commit proxies, resolvers, a global commit version, and replicated transaction logs.

1. The Mental Model

FoundationDB separates the transaction system from the storage system. Clients read versioned data directly from storage servers, but all writes flow through a transaction system that orders transactions, detects conflicts, and durably appends committed mutations to replicated transaction logs.

The central idea: a client reads a stable snapshot, buffers mutations locally, and submits one commit request. Resolvers validate optimistic conflict ranges. If validation succeeds, both sides of the transfer receive one commit version and become durable together in the TLog system.

Strict serializability

Ordinary transactions observe a consistent database version and use read/write conflict ranges so concurrent outcomes can be ordered as if transactions executed one at a time.

Optimistic concurrency

Resolvers do not lock Alice or Bob during the transaction. At commit, they compare the transaction's read ranges with writes committed after its read version.

Unbundled durability

Commit acknowledgement waits for the replicated TLog system, not for every storage server to persist its shard. Storage servers apply the durable log stream asynchronously.

Versioned visibility

Both mutations share a commit version. A read at that version waits for each selected shard to catch up, preventing a reader from observing only half of the transfer.

FoundationDB's commit path is not two-phase commit across storage shards. Storage servers do not prepare, vote, or participate synchronously in commit.

2. Example: Transfer $100 Across Two Shards

Assume Alice's balance key is stored on Storage Shard A, Bob's balance key is stored on Storage Shard B, and the small transfer marker is colocated with Shard A. The transaction uses a stable transfer ID so an unknown commit result can be retried safely.

transaction transfer("TX-42", 100):
    if GET("transfers/TX-42") exists:
        return "already applied"

    alice = GET("accounts/alice")  // Storage Shard A
    bob   = GET("accounts/bob")    // Storage Shard B

    if alice < 100:
        abort "insufficient funds"

    SET("accounts/alice", alice - 100)
    SET("accounts/bob",   bob + 100)
    SET("transfers/TX-42", "complete")

    COMMIT

The transaction preserves two invariants: Alice cannot overdraw based on the snapshot it read, and the debit, credit, and completion marker commit atomically. Ordinary reads add read conflict ranges; the three writes add write conflict ranges.

Why the transfer ID matters: after commit_unknown_result, the client cannot know whether the old attempt committed. Retrying with the same ID lets one transaction check the marker and either return safely or perform the transfer once.

3. Components on the Transaction Path

Component Responsibility
Client library Obtains a read version, routes reads to storage servers, overlays read-your-writes, buffers mutations and conflict ranges, sends commit, and runs retry logic.
GRV proxy Supplies a live database read version and participates in admission control. “GRV” means get read version.
Commit proxy Batches commit requests, obtains a commit version, fans conflict ranges out to resolvers, tags mutations for storage teams, pushes the log system, and replies to clients.
Master / sequencer Allocates monotonically increasing versions and tracks the transaction-system generation. The paper calls this role the Sequencer; current source still uses historical Master naming.
Resolvers Partition conflict ranges and hold recent in-memory write history. They decide whether a transaction's reads conflict with newer committed writes.
TLogs / log system Durably replicate the ordered, tagged mutation stream. Their acknowledgement is the commit durability point.
Storage servers Own key-range shards, serve MVCC reads, pull tagged mutations from TLogs, apply them in version order, and persist/coalesce them asynchronously.

Architecture Graph

The read and commit paths branch differently. Reads bypass commit proxies, while commit flows through resolvers and TLogs before storage servers consume the durable mutations.

4. Step-by-Step Transaction Lifecycle

  1. Get one read version

    The first database read lazily asks a GRV proxy for a live committed version, R. Every storage read in this transaction uses that same version. This creates a consistent snapshot even though Alice and Bob live on unrelated shards.

  2. Read the storage servers directly

    The client library resolves each key's shard location and load-balances reads to storage-server replicas. If a chosen replica has not applied version R, it waits or the client retries another replica. Reads do not pass through a commit proxy.

  3. Buffer mutations and conflicts in the client

    SET does not immediately contact a storage shard. The client records mutations in its read-your-writes layer and overlays them on later reads. Ordinary reads and writes produce ranges similar to:

    read conflict ranges:
  ["accounts/alice", keyAfter("accounts/alice"))
  ["accounts/bob",   keyAfter("accounts/bob"))
  ["transfers/TX-42", keyAfter("transfers/TX-42"))

write conflict ranges:
  the same three key ranges

mutations:
  Alice = 900
  Bob = 600
  TX-42 = "complete"

  4. Send one commit request

    The client submits the read version, buffered mutations, read conflict ranges, and write conflict ranges to one commit proxy. The proxy combines it with other requests in a short adaptive batch.

  5. Assign a commit version to the batch

    The commit proxy asks the master/sequencer for a new version, V, before resolver checking. Several transactions in one batch can share V; a transaction index provides ordering within that batch. A rejected transaction can therefore consume a version.

  6. Check conflicts at every relevant resolver

    The proxy partitions conflict ranges by the resolver key-space map. A resolver rejects this transaction if a committed write after R overlaps one of its read conflict ranges. Alice's and Bob's ranges may be checked by different resolvers, and the proxy admits the transfer only if all relevant resolvers admit it.

    Conflict rule: a transaction reading at R conflicts when a write ordered after R but before this transaction overlaps one of its read conflict ranges. Resolvers compare ranges and versions—not values.

  7. Tag mutations for destination storage teams

    The commit proxy uses its shard map to attach the Alice storage-team tag to the debit and the Bob storage-team tag to the credit. Both remain part of one versioned mutation stream; storage servers are not asked to prepare them.

  8. Push the mutation batch to replicated TLogs

    The log system durably appends the ordered mutations under version V. The proxy waits for the configured durable quorum in each applicable log set—not every TLog in the cluster and not the destination storage servers.

  9. Return commit success

    After TLog durability, the proxy reports the live committed version and returns V plus the transaction's batch index. Conflict returns not_committed; an unresolvable old read version returns transaction_too_old.

  10. Apply mutations asynchronously

    Storage servers continuously pull their tagged TLog streams, apply mutations in version order, and later persist/coalesce them into their storage engines. Old mutation-log entries and MVCC versions are removed as the durable and oldest-readable frontiers advance.

5. Why Readers Cannot See Half the Transfer

Storage Shard A and Storage Shard B can physically apply version V at different wall-clock times. Atomicity comes from versioned reads and the durable global mutation order, not synchronized disk writes.

  1. A later transaction obtains a read version at or above V.
  2. Its Alice read asks Shard A for that version; its Bob read asks Shard B for the same version.
  3. If either shard is behind, that read waits until the shard has consumed the TLog stream through the requested version.
  4. Once both return, the snapshot contains both mutations. A transaction reading an older version contains neither.

During recovery, the transaction system establishes the durable committed prefix from TLogs. Storage servers can roll back speculative versions beyond that prefix before serving the new epoch.

6. Conflict Semantics

Operation Conflict behavior Transfer consequence
Ordinary read Reads at R and adds a read conflict range. Two read-modify-write transfers touching Alice cannot both commit from stale balances.
Snapshot read Reads the same consistent snapshot but omits the read conflict range. A newer overlapping write does not force this transaction to conflict. It is unsuitable for enforcing the no-overdraft check by itself.
Set / clear Adds a mutation and a write conflict range, but a blind write has no implicit read range. Two blind writers are not inherently rejected merely because their write ranges overlap; conflict detection is driven by read-versus-write overlap.
Atomic operation Buffers a server-applied mutation without reading the old value, so the operation itself does not create a read conflict. Atomic add/subtract can update counters without conflicts, but validating “Alice has at least $100” requires an ordinary read or explicit conflict protection.
Read-your-writes The client overlays local buffered mutations on storage results; enabled by default, including for snapshot reads. Code later in the same transaction sees the proposed balances before commit.

7. Failures, Retries, and Unknown Results

Result or failure Meaning Correct response
not_committed A resolver detected a conflict; none of this transaction's mutations committed. Retry the whole transaction with a fresh read version.
transaction_too_old The resolver no longer retains enough recent conflict history to validate the old read version. Retry from the beginning. The often-mentioned time window is approximate and configuration/version dependent.
commit_unknown_result The request may have become durable, but the reply was lost or the transaction system changed epochs at the critical point. Do not blindly repeat a non-idempotent action. Retry using the same external transfer ID and completion marker.
Storage-server failure after acknowledgement The committed mutations remain in the replicated TLog system. The system recruits or repairs storage replicas and replays the durable stream; the transfer is not undone.
Transaction-system / TLog failure Recovery starts a new epoch and determines the durable committed prefix from surviving logs. The client retries retryable errors. Storage servers roll back any speculative versions beyond the recovered prefix.

Safe Retry Pattern

transfer_id = generate_once_outside_retry_loop()

retry:
    tr = begin()
    try:
        if tr.get("transfers/" + transfer_id) == "complete":
            return success

        // ordinary reads establish conflict ranges
        alice = tr.get("accounts/alice")
        bob = tr.get("accounts/bob")

        tr.set("accounts/alice", alice - 100)
        tr.set("accounts/bob", bob + 100)
        tr.set("transfers/" + transfer_id, "complete")
        tr.commit()
        return success
    catch retryable_error as error:
        tr.on_error(error)
        goto retry

9. Corrections to Common Misconceptions

Simplified claim More accurate model
“FoundationDB runs 2PC across storage shards.” Storage servers do not prepare or vote. The transaction system resolves conflicts and durably appends one versioned mutation stream to TLogs.
“Commit waits for Alice and Bob's storage servers.” Commit waits for required TLog durability. Storage servers consume and persist their tagged streams asynchronously.
“All reads pass through proxies.” The client gets a read version from a GRV proxy, then reads key ranges directly from storage-server replicas.
“Calling set() writes the destination shard.” The client buffers the mutation locally until commit.
“Resolvers compare account values or hold row locks.” Resolvers keep recent in-memory conflict-range history and compare range intersections across versions.
“Every transaction gets a unique timestamp.” A commit batch can share one version; transaction indices order transactions within that version.
“Snapshot read means latest or inconsistent data.” It reads the same consistent transaction version but does not add an automatic read conflict range.
“The paper's process names exactly match current code.” The paper uses Sequencer and Proxy as conceptual roles. Current code separates GRV and commit proxies, while sequencer implementation names still include Master.
“Current storage servers necessarily use SQLite.” The 2021 paper describes that implementation. Current code supports storage-engine abstractions, so SQLite should not be treated as a timeless protocol requirement.
