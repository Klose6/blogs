Cassandra Storage-Attached Index

SAI is a secondary index that lives next to the data on each replica. A write updates a small in-memory index. Flush writes that index beside the new SSTable. A query searches those indexes for primary keys, then reads the matching rows the same way a normal read does.

1. The Idea

The partition key is how Cassandra finds a row. A query on some other column, such as a name or an age, would otherwise scan every partition the replica owns. SAI stores, for that column, a map from the column value to the primary keys that contain it.

The index is local. It is not a hidden table that other nodes write into. Each replica indexes only the rows it stores. The coordinator still sends the query to the replicas that own the token ranges, at the consistency level you asked for. Those replicas use SAI, then return rows.

What SAI stores: a term, or a number, or a vector, pointing at row ids. The row itself stays in the memtable and the SSTable. After the index names a primary key, Cassandra reads that key and applies timestamps and tombstones as usual.

2. The Example

The rest of this page uses one table and two indexes. id is the partition key, so it does not need an index. name and age do.

CREATE TABLE person (
    id int,
    name text,
    age int,
    PRIMARY KEY (id)
);

CREATE INDEX ON person (name) USING 'sai'
    WITH OPTIONS = {'case_sensitive': false};

CREATE INDEX ON person (age) USING 'sai';

INSERT INTO person (id, name, age) VALUES (1, 'John', 21);
INSERT INTO person (id, name, age) VALUES (2, 'john', 50);
INSERT INTO person (id, name, age) VALUES (4, 'Caleb', 34);

Two queries show the two index shapes. The name query is an equality lookup. The age query is a range. A query that uses both is the intersection of those two answers.

SELECT * FROM person WHERE name = 'John';
SELECT * FROM person WHERE age >= 18 AND age <= 35;
SELECT * FROM person WHERE name = 'John' AND age <= 35;

Because the name index was created with case_sensitive: false, both John and john match the first query. The age query returns id 1 and id 4. The combined query returns only id 1.

3. The Pieces

One table can have many SAI indexes. They share one group so the expensive part, turning a row id back into a primary key, is stored once per SSTable.

One index per column

StorageAttachedIndex is the index on name or on age. It knows the column type, the analyzer, and how to search its own memtable and SSTable indexes.

One group per table

StorageAttachedIndexGroup holds every SAI index on person. On a write it updates all of them. On a flush it writes the shared SSTable files plus one index per column.

Memtable index

While the row is still in memory, a trie maps the term to primary keys. Numbers use the same in-memory structure. Vectors use a separate in-memory graph.

SSTable index

After flush, text terms sit in a byte-ordered trie. Numbers sit in a balanced tree. Both point at posting lists of row ids. Vectors sit in an on-disk nearest-neighbor graph.

On disk Shared or per column What it holds
Terms trie Per text column John points at the posting list for that term.
Balanced tree Per numeric column A range such as ages 18 through 35 walks the tree and collects posting lists.
Posting lists Per column The row ids inside this SSTable that contain the term.
Row-to-key map Once per SSTable Row id to token, partition key, and clustering key. Every column index on the table uses it.
Completion marker Per column and per SSTable Written only after the index files finished. A missing marker means the index must be rebuilt.

4. Write and Flush

The row is written first, through the normal commit log and memtable. SAI is told about the row in the same mutation. It does not do a read-before-write, and it does not index a row that has no live cells.

  1. The insert hits the memtable

    INSERT (1, 'John', 21) is an ordinary mutation. After the partition update is applied, the index group sees a live row and calls each column indexer.

  2. Each column records the term

    The name index stores John pointing at primary key 1. With case-insensitive analysis, the stored term is the normalized form, so a later search for john finds it. The age index stores 21 pointing at the same primary key. The second insert, id 2, adds john and 50. The third adds Caleb and 34.

  3. Flush assigns a row id

    Rows are written to the new SSTable in token order. Each live row gets the next row id, starting at 0. Suppose this flush writes id 1, then id 4, then id 2. They might become row ids 0, 1, and 2. The order is token order, not the order of the inserts. Range tombstones and rows with no live data are skipped, so they get no row id.

  4. Shared files, then each column

    One set of files records row id 0 as partition key 1, row id 1 as partition key 4, and row id 2 as partition key 2. The name index then writes its trie: the normalized term for John points at row ids 0 and 2, and Caleb points at row id 1. The age index writes its tree: 21 points at row id 0, 34 at row id 1, 50 at row id 2. A completion marker is written only after those files succeed.

Compaction does the same job again. It merges SSTables, so it builds a new shared key map and new column indexes for the output files. The old index files go away with the old SSTables.

5. A Query

Take SELECT * FROM person WHERE name = 'John' AND age <= 35. This is not a partition-key lookup. The coordinator treats it as a range read over the token ring and asks the replicas that cover those ranges. Each replica runs SAI locally, then returns the rows that still match.

  1. Search every copy of each index

    The name predicate searches the memtable trie and every SSTable trie for the normalized term john. Each hit is a row id. The shared key map turns that row id into primary key 1 and primary key 2. The age predicate searches the numeric tree for 18 through 35 and gets primary keys 1 and 4. Memtable hits are already primary keys, so they skip the row-id map.

  2. Keep keys that satisfy every predicate

    The two lists are walked together in primary-key order. Only key 1 is in both. That is the intersection. An OR would keep the union instead. If the query is not allowed to filter strictly, unrepaired SSTables are handled so a partial update on one column is not dropped before the row is read.

  3. Read the row, then check it again

    Key 1 is read from the memtable and the SSTables with the normal partition read. The index can be ahead of a delete, or a newer write can have changed the cell. Post-filtering drops the row if the current cells no longer match name = 'John' and age <= 35. The coordinator then merges replica answers the same way it merges any other read.

Why the second check exists: SAI indexes the value at write time and does not remove entries on delete. The row read is what sees the tombstone or the newer value. The index is a candidate list, not the final answer.

6. Deletes

Delete id 1. The mutation writes a tombstone into the memtable. The index group sees a row with no live data and does not update the name or age index. The on-disk posting list still says row id 0 once that row has been flushed.

The next query for name = 'John' still finds key 1 in the index. The row read then sees the tombstone and drops the row, so the client does not get id 1. Compaction later rewrites the SSTable without that live row, and the new index files no longer contain it.

That is why a delete does not have to find and edit every posting list. It also means an index with many deleted keys still points at rows the query will throw away. The cost shows up as extra partition reads, the same way tombstones cost a normal read.

7. Vector Search

A vector<float, n> column uses the same group, the same row ids, and the same final row read. The index structure is different. Instead of a trie or a number tree, the memtable keeps an in-memory graph and the SSTable keeps an on-disk approximate nearest-neighbor graph. A query uses ORDER BY embedding ANN OF [..] LIMIT k.

The replica asks each memtable and SSTable graph for neighbors, merges them by score, and keeps the best matches. It then reads those primary keys and returns them in primary-key order after the top-k selection, because Cassandra streams partitions in token order. In this tree the vector index is marked experimental: the code rejects consistency above ONE or LOCAL_ONE, paging, queries without LIMIT, and several other clauses.

Source Map

Names below are from Cassandra 5.0.

  • StorageAttachedIndexGroup
    Updates every column index on a live row, and creates the flush writer for the SSTable.
  • StorageAttachedIndex
    One column: type, analyzer, memtable index, and the SSTable indexes for that column.
  • TrieMemoryIndex
    In-memory term to primary keys, used until the memtable flushes.
  • StorageAttachedIndexWriter
    Assigns row ids during flush and writes the per-SSTable key map plus each column index.
  • IndexComponent
    The on-disk pieces: terms trie, balanced tree, posting lists, and the shared row-id map.
  • QueryController
    Intersects or unions the key lists, then reads each surviving primary key.
  • StorageAttachedIndexSearcher
    Runs the local search. Vector queries take a top-k path before the row read.

The shorter placement of SAI inside the rest of the node is in Cassandra Main Components.
