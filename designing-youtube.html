Designing YouTube

Video processing Object storage CDN 15 min read

How do we accept massive video uploads, transcode each file into many formats, and stream billions of playbacks globally? The core design separates durable media processing from low-latency video delivery.

01 / SCOPE

Design video on demand first

Users upload videos, creators manage metadata and visibility, and viewers search for and stream content on many devices. This design covers video on demand. Live streaming and recommendation-model training are separate systems with different latency requirements.

Functional

  • Resumable video upload and processing
  • Adaptive playback on web, mobile, and TV
  • Titles, descriptions, thumbnails, and search
  • Views, likes, comments, and subscriptions

Non-functional

  • High upload durability and playback availability
  • Playback starts in under two seconds at p95
  • Globally low buffering through edge delivery
  • Eventual consistency for counts and search
The dominant cost is video bytes, not API calls. Upload control, metadata, and engagement are ordinary distributed services; transcoding, storage, and CDN egress drive the design.
02 / CAPACITY

Estimate media separately from metadata

Assume 500 hours uploaded each minute, a 5 Mbps average source bitrate, five encoded renditions totaling 8 Mbps, and 100 million daily viewers watching 30 minutes each at an average 3 Mbps.

The exact numbers matter less than their shape: uploads are large and asynchronous, encoded media grows by several copies per source, and playback bandwidth is orders of magnitude larger than metadata traffic. Clients should transfer bytes directly to object storage and fetch playback segments from a CDN.

03 / HIGH LEVEL

Split control plane from media plane

API calls branch into metadata, search, and workflow systems; large video bytes travel directly between clients, S3, workers, and the CDN.

Control plane

APIs authenticate users, create upload sessions, store metadata, authorize playback, and orchestrate processing state.

Media plane

Object storage receives source files, workers create renditions, and CDNs deliver immutable manifests and segments to viewers.

  1. Create a session. The Go API authenticates the creator, checks quota, creates a private video row, and starts an S3 multipart upload.
  2. Send chunks directly. The client uploads parts to S3 using short-lived presigned URLs and retries failed parts.
  3. Finalize safely. The API validates uploaded part checksums, completes the multipart object, and emits an event.
  4. Process asynchronously. Kafka triggers malware scanning, metadata extraction, moderation, and transcoding.

The API never proxies multi-gigabyte video bytes. Multipart upload supports pause and resume, parallel chunks, integrity checks, and cleanup of abandoned sessions. Keep source objects private and encrypt them with a managed KMS key.

An orchestrator expands one uploaded source into independent jobs: probe codecs, scan content, generate thumbnails and captions, encode each resolution, package segments, validate outputs, then publish the manifest. Independent jobs run in parallel.

Rendition ladder

ResolutionTypical bitrateCodec

Select the ladder from source resolution, frame rate, motion, and popularity prediction. AV1 reduces delivery bytes but costs more compute, so encode it first for videos likely to receive many views.

Idempotency: key every output by video_id + source_version + profile_version. Retries overwrite or detect the same artifact rather than creating conflicting versions. Publish only after all required outputs pass validation.
06 / DELIVERY

Stream small immutable segments

  1. The viewer requests video metadata and playback authorization.
  2. The API returns a signed HLS or MPEG-DASH manifest URL.
  3. The player chooses a rendition from bandwidth, viewport, and buffer health.
  4. It downloads two-to-six-second segments from the nearest CDN edge.
  5. Adaptive bitrate logic moves up or down without restarting playback.

Segment files are immutable and content-versioned, so CDN entries can use long cache lifetimes. Manifests may have shorter TTLs when visibility or available renditions can change. Use origin shield caches to stop a newly viral video from overwhelming object storage.

Cache hit

The edge serves bytes near the viewer with low latency and no origin work.

Cache miss

The edge fetches once through a regional shield, caches the segment, and serves later viewers.

Signed cookies are usually better than signing every segment URL: they authorize a path prefix for a short playback session without generating thousands of unique cache keys.

07 / DISCOVERY

Store metadata by access pattern

DataStoreReason
Users, channels, video state PostgreSQL Transactions, constraints, and creator management
Comments and subscriptions Cassandra High write scale and partitioned timeline reads
Search documents OpenSearch Text analysis, ranking, filters, and autocomplete
Hot metadata Redis Low-latency cache for viral videos and channels
Video bytes S3 Durable, cheap, effectively unlimited object storage

After a metadata transaction commits, publish an outbox event to Kafka. Consumers update OpenSearch, invalidate Redis, and notify subscribers. Search may lag the source database by seconds; the video page reads authoritative visibility before returning playback credentials.

08 / COUNTERS

Do not write one row per view synchronously

Players send heartbeats containing watch duration, position, and a session ID. The event API validates basic fields and appends events to Kafka. Flink deduplicates retries, detects obvious bots, and aggregates views and watch time into minute buckets. 

playback event
  → Kafka partitioned by video_id
  → Flink validation + session deduplication
  → ClickHouse analytics
  → compacted counters in Cassandra / Redis

Displayed counts are eventually consistent and can be approximate. Likes are different: a user should have at most one active like per video, so store (user_id, video_id) idempotently and update the displayed total asynchronously.

Subscription feeds can fan out new videos to ordinary subscribers on publish. For channels with millions of subscribers, use fan-out on read to avoid a huge write burst, then merge those channel posts into the viewer's home timeline.

09 / FAILURE HANDLING

Prefer repairable asynchronous work

  • Upload interruption: retain multipart state so the client resumes only missing chunks.
  • Duplicate events: use video ID, source version, and job type as an idempotency key.
  • Transcoder failure: retry with exponential backoff, then move poison jobs to a dead-letter topic.
  • Regional outage: route APIs to another region and serve replicated media from the CDN.
  • CDN failure: use multiple CDN providers for high-value markets and keep origin failover available.
  • Bad encoding release: preserve the source and rerun a previous profile version.

Store source media and manifests in cross-region replicated buckets. Metadata databases need tested backups and point-in-time recovery. CDN loss should reduce performance, not destroy the only media copy.

A video becomes PLAYABLE after one baseline rendition and manifest are valid; higher resolutions can appear later. This reduces creator wait time without exposing incomplete artifacts.

11 / PRODUCTION

Measure viewer experience end to end

Media pipeline

  • Upload completion and checksum failures
  • Queue age and time to first playable rendition
  • Encoding failures by codec and profile
  • Source-to-output duration and cost

Playback quality

  • Time to first frame
  • Rebuffer ratio and playback failures
  • Average delivered bitrate
  • CDN hit ratio and origin egress

Instrument clients with session-level quality-of-experience events and aggregate them by device, ISP, region, CDN, and player version. Server health can look perfect while one ISP or television client produces a poor viewing experience.

Final design summary

Clients upload directly to S3 in resumable parts. Kafka and Temporal coordinate idempotent FFmpeg jobs that create HLS and DASH renditions. CloudFront serves immutable segments near viewers. PostgreSQL, Cassandra, Redis, and OpenSearch handle distinct metadata access patterns, while Flink aggregates high-volume playback events. The architecture scales because large video bytes bypass application servers on both upload and playback.
