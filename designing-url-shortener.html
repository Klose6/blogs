Designing a URL Shortener

Key generation Caching Multi-region 12 min read

How do we turn long URLs into compact links that redirect in milliseconds, survive viral traffic, and remain safe to operate? The design optimizes a read-heavy hot path without weakening creation correctness or abuse controls.

On this page Requirements Capacity Short-code choices Architecture Creation path Redirect path Storage Multi-region Abuse and safety Analytics Technology stack
01 / SCOPE

Make redirects fast and links durable

Users submit a long URL and receive a short link. Visiting the short link redirects to its destination. Optional features include custom aliases, expiration, link disabling, and click analytics.

Functional

  • Create random or custom short links
  • Redirect to the original destination
  • Expire, disable, and delete owned links
  • Report asynchronous click analytics

Non-functional

  • Redirect latency below 50 ms at p99
  • 99.99% redirect availability
  • No two active links share a code
  • Links remain available across regions
Scope decision: destinations are mutable only for authenticated owners. Publicly changing a link after distribution creates phishing risk and makes caches harder to reason about.
02 / CAPACITY

Expect far more redirects than writes

Assume 100 million new links and 10 billion redirects each day, with a 5× peak multiplier. A mapping record averages 1 KB after indexes and metadata.

The 100:1 read-to-write ratio makes edge and Redis caching highly effective. Analytics volume is comparable to redirect volume, but analytics must never delay the redirect response.

03 / KEY GENERATION

Prefer random Base62 codes

Base62 uses digits, lowercase letters, and uppercase letters. Ten characters provide 62¹⁰ ≈ 8.39 × 10¹⁷ possible codes. Generate bytes with a cryptographically secure random source, encode them, and use a conditional database insert to detect the extremely unlikely collision.

Do not compute hash(long_url) as the identifier. Different owners may want separate expiration and analytics for the same destination. Instead, support idempotent creation using a client-provided idempotency key.

05 / CREATION

Validate before publishing a link

POST /v1/links
Idempotency-Key: 0199f02d-...
{
  "url": "https://example.com/articles/system-design",
  "custom_alias": null,
  "expires_at": "2027-09-14T00:00:00Z"
}

201 Created
{
  "code": "q7Ba31ZmP2",
  "short_url": "https://sho.rt/q7Ba31ZmP2"
}
  1. Authenticate and rate-limit. Apply stricter limits to anonymous users and custom-alias attempts.
  2. Normalize and validate. Accept only HTTP(S), enforce length limits, canonicalize the host, and reject internal network destinations.
  3. Check reputation. Evaluate blocklists, domain age, malware signals, and account trust before activation.
  4. Claim the code. Use DynamoDB conditional attribute_not_exists(code); regenerate on collision.
  5. Warm and respond. Populate Redis and return only after the durable mapping exists.

Custom aliases use the same conditional insert and namespace as generated codes. Reserve system paths such as api, admin, and health. Normalize alias case if links should be case-insensitive.

06 / HOT PATH

Resolve through layered caches

  1. A Cloudflare Worker checks its internal mapping cache for popular immutable links; this is separate from browser redirect caching.
  2. The Go service checks a bounded in-process TinyLFU cache.
  3. On a local miss, it reads the regional Redis Cluster.
  4. On a Redis miss, it performs a strongly or eventually consistent DynamoDB read according to the link's age.
  5. It returns the redirect immediately and publishes analytics through a non-blocking local Kafka producer. 
HTTP/1.1 302 Found
Location: https://example.com/articles/system-design
Cache-Control: private, no-store

Use 302 by default. Browsers and intermediaries may cache 301 redirects permanently, preventing destination changes, disablement, and accurate analytics. For immutable links, an owner can explicitly opt into a cacheable 301 or 308 response.

Negative caching

Cache unknown codes for a short period, such as 30 seconds, to stop random scans from repeatedly hitting DynamoDB. Invalidate the negative entry after a successful creation of that code.

Analytics never blocks redirect. If Kafka is unavailable, buffer a bounded number of events locally and then sample or drop analytics. Sending the user to the destination is the primary availability goal.
07 / DATA MODEL

Key mappings by short code

URLMapping {
  code            string       // partition key
  destination     string
  owner_id        string
  created_at      timestamp
  expires_at      timestamp?
  status          ACTIVE | DISABLED | BLOCKED
  redirect_type   302 | 301
  version         integer
}

The dominant lookup is code → destination, which maps directly to a DynamoDB partition key. Keep an owner-to-links index for management pages, but do not make redirect depend on that index. DynamoDB TTL removes expired records eventually; the application must still check expires_at because TTL deletion is not immediate.

Cache correctness

Cache values include mapping version, status, and expiration. An update writes DynamoDB first, then publishes an invalidation event. Short TTLs bound stale redirects if invalidation is lost. Blocking a malicious link writes a high-priority deny entry to every regional Redis cluster before asynchronous cache cleanup.

08 / MULTI-REGION

Read locally, give each code one writer

DynamoDB Global Tables replicate mappings to each region, and every region has its own Redis cache and stateless redirect service. Redirects use the nearest healthy region and tolerate replication lag for newly created links.

Multi-active conditional writes are not enough for strict custom alias uniqueness: two regions can claim the same absent alias before replication converges. Route creation by hash(code) to a deterministic home region. That region is the single writer for the code; all regions remain readers.

New generated link

Random codes are generated near the user, then claimed in the code's home region. Cache the result locally after success.

Home-region outage

Existing links still redirect globally. Pause custom creation for affected keys rather than risk duplicate ownership.

09 / TRUST

A shortener is also an abuse platform

  • SSRF: reject loopback, link-local, private, and cloud-metadata destinations after DNS resolution.
  • Phishing: scan destinations at creation and periodically after redirects begin.
  • Malware: integrate browser-safe browsing feeds and internal reputation models.
  • Enumeration: use CSPRNG codes and return uniform errors for unknown or blocked links.
  • Bot traffic: rate-limit by account, IP, ASN, and behavioral signals.
  • Takedowns: maintain an auditable moderation workflow and globally fast deny propagation.

A destination can become malicious after creation or redirect through several domains. Run asynchronous rescans and disable links when reputation changes. Show an interstitial for suspicious destinations instead of silently forwarding users.

10 / EVENTS

Aggregate clicks asynchronously

redirect event
  → Kafka partitioned by code
  → Flink bot filtering + deduplication
  → minute aggregates
  → ClickHouse reports
  → S3 + Parquet archive

Events include code, timestamp, coarse geography, referrer domain, device category, edge region, and a privacy-safe session hash. Do not store raw IP addresses indefinitely. Flink uses event-time windows and tolerates late edge events.

Dashboard counts are eventually consistent and may exclude known bots. Billing-grade links need immutable raw events, versioned fraud rules, and periodic reconciliation—the same correctness pattern as an ads click aggregator.

Production signals

  • Redirect latency and availability by region
  • Edge, local, and Redis cache hit rates
  • DynamoDB throttling and replication lag
  • Creation collisions and custom-alias conflicts
  • Blocked-link traffic and reputation-scan age
  • Kafka producer drops and analytics consumer lag

Final design summary

Generate unguessable ten-character Base62 codes and claim them with conditional writes. Store mappings in DynamoDB, resolve popular links through Cloudflare and Redis, and keep the Go redirect path independent from analytics. Give each code one write region while replicating reads globally. Kafka, Flink, ClickHouse, and S3 handle click reporting without delaying redirects, while continuous safety scanning limits the abuse inherent in public short links.
