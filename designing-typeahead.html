Designing Typeahead

Prefix search FST indexes Ranking 13 min read

How do we return useful suggestions after every keystroke in a few milliseconds while trends, language, safety rules, and personal history keep changing? The design combines compact prefix snapshots with a small real-time delta index.

01 / SCOPE

Suggest intent before search begins

The service accepts a partial query and returns a small ranked list of query, entity, or product suggestions. Results account for locale, market, device, current trends, and—when permitted—personal history. Full document search remains a separate downstream system.

Functional

  • Prefix completion across languages and scripts
  • Popularity, freshness, and quality ranking
  • Optional personalization and typo correction
  • Safety filters, blocklists, and editorial controls

Non-functional

  • Server latency below 30 ms at p99
  • High availability during index rebuilds
  • Trending suggestions visible within minutes
  • No partial or mixed index version during rollout
Product boundary: typeahead optimizes for a handful of highly likely completions, not exhaustive recall. Returning the best 10 suggestions quickly is more important than finding every string that shares a prefix.

03 / INDEX

Store top results at each prefix

StructureStrengthWeakness
Trie Natural O(prefix length) lookup and easy updates Pointer-heavy and expensive for large vocabularies
Sorted array Compact and simple range search by binary search Must scan or maintain extra ranking data
Finite-state transducer Shares suffixes, compresses strings, and supports weighted lookup Usually immutable and expensive to update in place
Search engine Built-in analyzers, fuzzy search, and operational tooling More latency and memory than a specialized top-K index

Use an immutable weighted FST for the large baseline and a small mutable trie for fresh trends and editorial changes. Each prefix stores or can traverse to its top K suggestion IDs, avoiding a scan of all matching strings.

04 / HIGH LEVEL

Separate serving from index production

Serving merges an immutable FST, a fresh delta trie, cache hits, and optional personal signals; the indexing plane builds each input separately.

05 / REQUEST PATH

Do little work after each keystroke

GET /v1/typeahead
  ?q=distri
  &locale=en-US
  &market=US
  &limit=10
  &session_id=0199...

{
  "suggestions": [
    { "text": "distributed systems", "type": "query" },
    { "text": "distributed cache",   "type": "query" }
  ],
  "index_version": "2026-09-19T17:00Z"
}
  1. Normalize. Apply Unicode normalization, locale- aware case folding, whitespace rules, and a maximum prefix length.
  2. Check caches. Read an in-process TinyLFU cache, then regional Redis for non-personalized prefix candidates.
  3. Route one shard. Hash the normalized (locale, prefix) to a replicated serving shard.
  4. Merge candidates. Combine baseline FST, delta trie, editorial entries, and optional personal history.
  5. Filter and rank. Enforce safety and policy first, score the remainder, deduplicate, and return the best results.

Clients debounce input by roughly 50–100 ms and cancel older requests. Every call carries a monotonically increasing client sequence so a late response for dis cannot replace the newer response for distri.

06 / INDEX PIPELINE

Build immutable snapshots, stream small changes

Candidate sources include successful search queries, clicks, catalog entities, product inventory, editorial suggestions, and policy blocklists. Raw logs are not accepted blindly: remove bots, low-frequency strings, personal data, spam, and unsafe queries.

  1. Kafka collects query, impression, click, and corpus-change events.
  2. Flink deduplicates, detects trends, and maintains minute and hour aggregates by normalized query, locale, and market.
  3. Spark joins longer history, quality labels, and safety decisions, computes baseline weights, and builds partitioned weighted FSTs.
  4. Builders write immutable files, checksums, and a signed manifest to S3 under a new version.
  5. Serving nodes download, verify, memory-map, warm, and atomically swap the complete version without stopping queries.

The real-time trie holds only changes since the snapshot and has a strict memory cap. Once a new snapshot includes those events, advance its watermark and discard the covered delta. This prevents the mutable layer from growing without bound.

07 / RELEVANCE

Rank for completion probability and value

score =
    0.35 × log(popularity)
  + 0.25 × freshness_decay
  + 0.20 × prefix_completion_probability
  + 0.15 × personal_affinity
  + 0.05 × business_quality
  - policy_penalties

Actual weights come from offline evaluation and online experiments. Popularity uses a logarithm so one globally dominant query does not suppress every alternative. Freshness decays trending spikes; quality considers downstream engagement rather than raw impression count.

Personalization

Personal history contributes candidates only after authorization and user consent. Store a bounded, encrypted list of recent selected queries or entities keyed by user. Merge it late in the request so the global prefix result remains highly cacheable.

Never cache personalized output under a prefix-only key. Cache the global candidates, then rerank them with user features in memory. Provide history deletion and incognito modes that bypass personal signals.

08 / TYPOS

Use fuzzy matching only when it helps

Fuzzy lookup dramatically increases the candidate space. Do not run edit-distance search for empty, one-character, or already productive prefixes. Trigger it after three or more characters when exact prefix results fall below a threshold.

TechniqueExampleCost
Edit distance 1iphnoe → iphoneFST traversal with Levenshtein automaton
Keyboard adjacencygppgle → googleLanguage and layout-specific substitutions
Phonetic matchNames with similar pronunciationLocale-specific and prone to false positives
TransliterationLatin input to another scriptRequires language detection and alternate indexes

Penalize fuzzy candidates below exact matches unless engagement evidence strongly favors the correction. Return the intended suggestion text—not an invisible rewrite—and measure correction acceptance separately from normal completions.

09 / SCALE

Shard by normalized prefix, replicate hot ranges

Hash (locale, normalized_prefix) across virtual shards, so one lookup reaches one owner and traffic distributes more evenly than first-character partitioning. Each shard has replicas across availability zones and memory-maps only its FST partition.

Empty and very short prefixes remain hot regardless of hashing. Precompute them, replicate them to every API node, and refresh them frequently. For other viral prefixes, the local TinyLFU and Redis layers absorb traffic before it reaches FST shards.

Positive cache

Cache global top-K candidates by prefix, locale, market, index version, and policy version.

Negative cache

Cache no-result long prefixes briefly to stop repeated typo and bot traffic from reaching shards.

Version every cache key. Adding the snapshot and policy versions makes rollout invalidation implicit. Old entries expire naturally instead of requiring a global cache delete.
10 / TRUST

Prevent the system from amplifying harm

  • Minimum support: require enough distinct users before a query becomes globally eligible.
  • Bot resistance: downweight coordinated or automated query and click bursts.
  • PII removal: reject emails, phone numbers, account IDs, and rare person-specific strings.
  • Policy filters: apply locale, age, legal, and safety rules after every candidate merge.
  • Emergency removals: distribute a tiny signed denylist independently of full snapshots.
  • Experiment safety: keep editorial and policy overrides outside model-controlled scores.

Trending data is especially vulnerable because freshness rewards sudden volume. Require cross-user diversity, reputation-weighted support, anomaly detection, and a delay before an unseen query can enter the real-time trie.

11 / MULTI-REGION

Serve entirely from regional snapshots

Every region runs independent query replicas with the same signed baseline manifest. S3 cross-region replication distributes snapshot files; serving nodes activate only versions whose complete shard set, checksums, model, and policy bundle are available.

Kafka mirrors aggregated trend events rather than raw personal query logs when data residency requires it. Regional delta tries may differ briefly, which is acceptable. A control plane tracks rollout health and can pin or roll back each region atomically.

Indexing outage

Keep serving the last valid snapshot. Freshness degrades, but request availability and correctness remain intact.

Delta failure

Drop the mutable layer and serve baseline results. Never let a corrupt trend index take down typeahead.

Production signals

  • End-to-end and server latency by prefix length and locale
  • Suggestion selection, abandonment, and reformulation rate
  • Local cache, Redis, FST, delta, and fuzzy lookup hit rates
  • Snapshot age, regional version skew, and activation failures
  • Delta size, trend lag, and baseline fallback rate
  • Unsafe suggestion blocks, emergency removals, and abuse anomalies

Final design summary

Build compact weighted FST snapshots from cleaned query and corpus data, then memory-map them across sharded Go serving nodes. Flink maintains a bounded delta trie for fresh trends, while Ristretto and Redis absorb hot prefixes. The request path merges global, fresh, editorial, and optional personal candidates before safety filtering and ranking. Versioned immutable snapshots make regional rollout and rollback safe, and the baseline remains available whenever indexing, trends, or personalization fail.
