Designing Multi-Region High Availability

Regional cells Traffic steering Fencing 16 min read

How do we keep serving through a complete regional outage without creating split brain or corrupting state? The design uses independent regional cells, global traffic steering, explicit data ownership, and rehearsed failover—not merely duplicate infrastructure.

01 / SCOPE

Design for failures larger than a server

The service exposes stateless HTTP and gRPC APIs backed by durable transactional state, caches, queues, object storage, and background jobs. It must tolerate a complete region becoming unreachable while preserving authentication, core reads, and carefully defined writes.

Functional

  • Route users to healthy nearby regions
  • Preserve sessions and idempotent writes through failover
  • Recover background work without double effects
  • Support planned evacuation and regional maintenance

Non-functional

  • 99.99% API availability
  • Regional failover within five minutes
  • Documented data-loss bound per data class
  • No shared runtime dependency that defeats isolation
Multi-region is not automatically highly available. A global database, identity provider, deployment pipeline, secret store, or bad configuration can fail every region together. The design must reduce correlated failure, not only add copies.
02 / RECOVERY CONTRACT

Define RTO and RPO before architecture

Recovery Time Objective (RTO) is how long the service may be unavailable. Recovery Point Objective (RPO) is how much recently committed data may be lost. Different data classes deserve different cost and latency trade-offs.

Data classTarget RTOTarget RPOStrategy
Account and payment state< 5 minutes0Strong quorum spanning at least three failure domains
Core product records< 5 minutes< 30 secondsHome-region write, async replica, fenced promotion
Search and cache< 1 minuteRebuildableIndependent regional copies
Analytics events< 1 hour< 5 minutesBuffered streams and object-storage archive

RPO zero across distant regions requires synchronous agreement and therefore adds wide-area latency to every write. Do not promise it for every table when only a small financial subset needs it.

03 / TOPOLOGY

Choose active-active only where state allows it

ModelBenefitCost
Active-passive Simple ownership and conflict-free writes Idle capacity and slower, riskier promotion
Active-active stateless Low-latency reads and immediate traffic capacity Still needs an explicit state-write strategy
Multi-writer data Local writes in every region Conflicts, global quorum latency, or restricted data model
Home-region entities One writer per tenant or entity; reads active everywhere Some writes take a cross-region hop

Use active-active regional application cells, but assign each tenant or entity a home region for ordinary writes. Reads and conflict-safe operations run locally. This avoids pretending that arbitrary relational updates can merge safely after a partition.

04 / HIGH LEVEL

Build independent regional cells

Every region contains a complete serving cell. Cross-region links replicate durable state; they are not required for ordinary local reads.

A cell includes compute, load balancers, database replicas, cache, queue consumers, object-storage access, secrets, and observability. Regional APIs must not call another region synchronously for health checks, logging, configuration, or cache access.

05 / ROUTING

Fail traffic using several health signals

An anycast accelerator or global load balancer sends users to the nearest healthy regional endpoint. DNS remains useful for coarse control, but resolver caching makes low-TTL failover slower and less deterministic than connection-level anycast steering.

  1. Edge reachability. Confirm load balancer and TLS handshakes from several independent networks.
  2. Synthetic transactions. Exercise authentication, a representative read, and a safe write against the whole cell.
  3. Regional SLOs. Evaluate error rate, latency, saturation, replication lag, and dependency health.
  4. Quorum decision. Require sustained multi-signal failure before removing a region; avoid reacting to one noisy probe.
  5. Gradual restoration. Send 1%, then 10%, then more traffic after recovery instead of instantly returning the full load.
Automatic failover needs a circuit breaker. If destination regions lack headroom or data is too stale, shifting all traffic can turn one outage into three. Automation must check both source failure and target readiness.
06 / STATE

Sessions Signed stateless token plus regional refresh state Reauthenticate if refresh state is unavailable

Prevent split brain with fencing

Every home-region assignment has a monotonically increasing epoch. Writers include it in database mutations and downstream events. Promoting Region B first obtains epoch 43 from a globally consistent control record; Region A's old epoch 42 writes are then rejected even if it returns with stale routing. 

UPDATE tenant_record
SET value = ?
WHERE tenant_id = ?
  AND home_region = "region-b"
  AND epoch = 43;

Idempotency keys survive retries across regions. Keep them in the same durable scope as the business write; a regional in-memory deduplication cache cannot prevent duplicate payments after failover.

Conflict-safe active-active data

Some values merge safely: grow-only counters, sets with tombstones, and last-seen timestamps with deterministic tie-breakers. Use CRDTs or explicit merge rules only for those fields. Never apply last-write-wins blindly to balances, inventory, or permissions.

07 / HEADROOM

Provision for the largest credible loss

If three regions each run at 70% utilization, losing one requires the other two to absorb 50% more traffic, pushing them to 105%. That design is not region-failure tolerant.

regional capacity

Surviving cells handle peak traffic after one full cell loss.

< 60%

For three balanced regions before one-region failover.

2×

burst protection

Autoscaling is helpful but cannot replace warm baseline capacity.

Reserve quota, database connections, NAT capacity, IP addresses, Kafka partitions, and third-party limits—not only compute instances. Autoscaling may take minutes and often depends on the same cloud control plane affected by a regional incident.

08 / RECOVERY

Fail over state before accepting writes

  1. Declare the incident. Freeze automated deploys and configuration changes; record the last known replication watermark.
  2. Stop or fence old writers. Remove credentials, revoke leases, or advance the global epoch before promoting replicas.
  3. Promote durable state. Choose the recovery point, promote database and queue replicas, and validate invariants.
  4. Start background ownership. Resume schedulers and consumers with idempotency; expect inflight work to repeat.
  5. Shift traffic gradually. Begin with reads and canaries, then enable writes after synthetic verification.
  6. Reconcile after recovery. Compare logs, quarantine divergent writes, rebuild replicas, and only then return traffic.

Failback is a separate migration, not the reverse of a DNS change. Region A must rejoin as a clean replica of the new authority in Region B. Never let its stale database resume writes automatically.

09 / ISOLATION

Remove hidden global single points

  • Identity: cache signing keys and validate access tokens locally; keep emergency login paths.
  • Secrets: replicate encrypted secrets ahead of time; do not fetch them cross-region at startup.
  • Configuration: run from a last-known-good signed bundle when the control plane is unavailable.
  • Deployment: pin artifacts in every region and allow one region to deploy without another.
  • Observability: buffer telemetry locally; logging failure must not block requests.
  • Third parties: use regional endpoints, strict timeouts, circuit breakers, and degraded modes.
  • Certificates and DNS: pre-provision credentials and protect registrar changes with separate controls.

Use cell-local service discovery, cache, queues, and feature flags. A global control plane may distribute desired state, but every cell keeps and can run from a validated local copy.

10 / VALIDATION

Prove failover before the incident

Continuous tests

  • Terminate instances and availability zones
  • Inject dependency latency and packet loss
  • Verify target-region capacity and quotas
  • Restore backups into isolated environments

Game days

  • Evacuate a production region intentionally
  • Promote databases and queue ownership
  • Measure actual RTO, RPO, and duplicate effects
  • Practice failback and data reconciliation

Run regular “regional evacuation” drills with a controlled fraction of tenants before testing the full cell. A runbook that has never executed its database promotion, fencing, and rollback steps is only documentation—not a recovery capability.

Observe the user journey

Track availability and latency by region, operation, and data owner. Alert on replication lag, fencing epoch divergence, traffic-shift percentage, target saturation, queue age, cache coldness, and cross-region request count. Synthetic clients should continuously test authentication, reads, writes, and background completion.

The theoretical availability of two independent 99.9% regions is 99.9999%, but regions are not independent when they share code, operators, cloud control planes, or data systems. Measure observed end-to-end availability instead of multiplying provider SLAs.

Aurora Global Database is single-writer by default; promotion is not conflict-free active-active. DynamoDB Global Tables use last-writer- wins replication and are safe only when the application data model tolerates or resolves concurrent updates. Tool names do not remove those consistency constraints.

Final design summary

Run complete, independently operable cells in several regions and steer traffic through a health-aware global edge. Keep reads local, assign ordinary writes a home region, and reserve global quorum for the small set of data requiring RPO zero. Replicate durable state with explicit lag and ownership, fence old writers before promotion, provision N+1 capacity, and make retries idempotent. Most importantly, rehearse evacuation, promotion, reconciliation, and failback until the measured recovery objectives match the promises.
