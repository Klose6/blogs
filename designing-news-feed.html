Designing a News Feed

Hybrid fan-out Ranking Caching 14 min read

How do we publish a post once and deliver a relevant, fresh feed to millions of followers? The design combines materialized inboxes for fast reads with on-demand merging for high-fan-out creators.

01 / SCOPE

Build a personalized following feed

Users publish text, images, and videos; follow other users; and browse a ranked feed. They can like, comment on, hide, or delete posts. This design covers the following feed. Recommendation model training and advertising auctions are adjacent systems.

Functional

  • Create, edit, delete, and retrieve posts
  • Follow and unfollow creators
  • Return a ranked, paginated home feed
  • Capture likes, comments, hides, and views

Non-functional

  • Feed response below 300 ms at p99
  • New normal-author posts visible within seconds
  • No single celebrity can overload fan-out
  • Deleted or private content disappears quickly
Consistency priority: ranking and counters can be eventually consistent. Access control cannot. Every read performs a final visibility check even if a stale feed candidate remains.
02 / CAPACITY

Fan-out creates the real write load

Assume 100 million daily users, 500 million posts and 2 billion feed reads per day, a 5× peak multiplier, and 200 followers per creator on average.

Follower counts are highly skewed, so averages hide the dangerous case. A creator with 100 million followers cannot synchronously materialize 100 million inbox entries for every post.

03 / FAN-OUT

Combine fan-out on write and read

StrategyHow it worksTrade-off
Fan-out on write Insert the post ID into each follower's inbox at publish time Very fast reads, but expensive for celebrity authors
Fan-out on read Fetch recent posts from every followed author when the feed opens Cheap publishing, but slow reads and many scatter queries
Hybrid Push normal authors; merge celebrity posts during reads More logic, but controls both read latency and write explosions

Use fan-out on write below a configurable follower threshold, such as 100,000. Mark larger accounts as pull authors. The read service merges their recent posts with the user's materialized inbox before ranking. Measure fan-out cost and adjust the threshold dynamically.

04 / HIGH LEVEL

Branch publishing from feed serving

Kafka branches new posts into asynchronous fan-out; feed reads merge materialized inboxes with celebrity posts before ranking.

05 / PUBLISHING

Commit the post before distributing it

POST /v1/posts
Idempotency-Key: 0199f2d1-...
{
  "text": "A new system design note",
  "media_ids": ["media_842"],
  "visibility": "followers"
}
  1. Validate. Authenticate the author, rate-limit, scan text, and verify uploaded media ownership.
  2. Commit atomically. Write the post and an outbox event in one PostgreSQL transaction.
  3. Publish the event. A connector sends the outbox row to Kafka, keyed by author ID.
  4. Choose fan-out mode. Workers read follower pages for normal authors or update the celebrity recent-post list.
  5. Materialize. Batch inbox inserts and warm Redis for active followers; retry failed pages idempotently.

The API returns after the post and outbox commit, not after fan-out. Each inbox key contains (user_id, post_id), making worker retries safe. Publish progress is checkpointed by follower page so a worker crash does not restart a massive distribution.

06 / SERVING

Generate more candidates than the page needs

  1. Read a few hundred recent post IDs from the user's Redis inbox, falling back to Cassandra on a miss.
  2. Fetch recent posts from followed celebrity authors in parallel.
  3. Merge and deduplicate IDs, then remove blocked, deleted, expired, already-seen, or unauthorized candidates.
  4. Batch-fetch post bodies and ranking features.
  5. Score candidates, apply diversity rules, and return the top page with an opaque continuation cursor.

Cache post objects separately from user-specific feed results. Post objects have high reuse, while a fully ranked feed is personalized and becomes stale quickly. A short session cache can stabilize the next few pages for one reader.

Graceful degradation: if ranking is unavailable, return valid candidates in reverse chronological order. If Redis is unavailable, read a smaller page from Cassandra. The feed can lose personalization before it loses availability.
07 / RELEVANCE

Separate retrieval from ranking

Candidate retrieval answers “what could this user see?” Ranking answers “what should appear first?” Keeping them separate allows fast rules-based fallback and independent model deployment. 

score = model(
  viewer_author_affinity,
  predicted_like_probability,
  predicted_comment_probability,
  freshness,
  post_quality,
  negative_feedback_probability
)

final = diversity_and_policy_rules(score)

Online features—recent clicks, hides, and author interactions—live in Redis or a dedicated feature store. Durable events flow through Kafka and Flink into offline Parquet datasets for training and into the online store for serving. Every model and feature set is versioned so ranking decisions are reproducible.

After scoring, apply hard policy filters, author and topic diversity, frequency caps, and exploration. A high model score never overrides privacy, blocks, moderation, or legal restrictions.

08 / CURSORS

Avoid offset pagination

OFFSET 100 is slow and unstable while new posts arrive. Return an opaque, signed cursor containing a feed-session ID, candidate watermark, last score, last post ID, and expiry. 

{
  "items": [...],
  "next_cursor": "base64url(signed_session_state)",
  "generated_at": "2026-09-14T23:55:00Z"
}

The short-lived feed session stores a candidate snapshot or its seed and model version. This prevents severe reshuffling between pages. Clients still deduplicate by post ID because edits, deletes, retries, and session expiration can change results.

09 / CHANGES

Filter stale candidates at read time

Materialized inboxes intentionally contain references, not copies of post content. When a post is edited, the latest object appears automatically. Deletes and privacy changes write authoritative tombstones immediately and publish cleanup events.

ChangeImmediate actionAsync cleanup
Post deletedTombstone post and purge object cacheRemove inbox references
User unfollowsFilter author during feed readRemove old inbox entries
User blocks authorUpdate deny cache globallyClean feeds and notifications
Post becomes privateRequire authoritative access checkInvalidate cached candidates

Store a social-graph version with generated feed pages. If the viewer's block or membership version changes, discard the cached page. This prevents a long cache TTL from weakening access control.

10 / MULTI-REGION

Write users at home, serve feeds locally

Assign each user a home region for post and social-graph writes. Replicate post events globally through Kafka cluster linking and replicate durable stores asynchronously. Feed APIs run in every region and read local inbox replicas and caches.

Fan-out occurs near the followers' inbox partitions rather than only in the author's region. A distribution consumer receives the post event, groups followers by home region, and publishes regional fan-out tasks. This avoids millions of individual cross-region writes.

Regional outage

Route readers to another region and rebuild missing inbox pages from followed authors. New writes pause or use a fenced home-region failover.

Replication lag

A new remote post may appear seconds late. Preserve session consistency by reading the author's recent-post fallback when needed.

Production signals

  • Post-to-feed freshness by author class and region
  • Fan-out queue age, throughput, retries, and celebrity classification
  • Candidate count before and after safety filters
  • Feed latency split by retrieval, hydration, and ranking
  • Redis hit rate and Cassandra partition size
  • Model timeout, fallback rate, and engagement quality

Final design summary

Commit posts and outbox events in PostgreSQL, then distribute them through Kafka. Fan out normal authors into Cassandra and Redis inboxes, while merging celebrity posts at read time. Retrieve more candidates than needed, enforce current visibility, rank with versioned features, and paginate through stable feed sessions. Regional fan-out keeps writes local, and chronological fallback preserves availability when personalization fails.
