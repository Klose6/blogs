Designing an Ads Click Aggregator

Event streaming At-least-once Real-time OLAP 10 min read

How do we ingest millions of ad clicks, reject duplicates, publish fresh campaign metrics, and still produce correct billable totals? This design separates the fast serving path from the source of truth.

On this page Requirements Estimation Architecture Write path Aggregation Storage Correctness Scaling Operations
01 / SCOPE

Start with the contract

The service accepts click events from ad-serving clients and exposes aggregated counts to advertisers. A click may arrive late, be retried, or be malicious. The reporting UI should be fast and fresh; billing should favor correctness over immediacy.

Functional

  • Ingest a uniquely identified click
  • Aggregate by campaign, ad, geography, and time
  • Query near-real-time metrics and historical reports
  • Filter duplicates, bots, and invalid campaigns

Non-functional

  • 99.99% ingestion availability
  • Metrics visible within 60 seconds
  • No accepted event silently lost
  • Auditable and replayable billing totals
Key design choice: “exactly once” is an end-to-end business property, not a message-broker checkbox. Use at-least-once delivery plus idempotent processing and periodic reconciliation.

03 / HIGH LEVEL

Separate ingest, compute, and serve

Kafka branches into a live Flink path and an immutable S3 truth path; reconciliation later corrects the same ClickHouse serving tables.

Fast path

Flink validates, deduplicates, and updates minute buckets. ClickHouse serves dashboards within seconds.

Truth path

Every accepted raw event lands in S3. Scheduled Flink batch jobs replay and reconcile final totals for billing.

Should this use Lambda architecture?

A classic Lambda architecture runs two independent implementations: a speed layer for recent events and a batch layer that recomputes authoritative views. It fits ad billing because raw clicks must be retained, real-time totals may be provisional, and late or corrected events must eventually produce exact invoices.

The drawback is duplicated business logic, operational cost, and possible disagreement between the two layers. For this service, use a Lambda-inspired, streaming-first design: Kafka is the replayable log, Flink powers the live pipeline, S3 is the long-term source of truth, and the same versioned validation and aggregation rules run during reconciliation. This is simpler than maintaining separate stream and batch codebases while retaining the correctness benefit of a batch truth path.

Recommendation: do not add a batch layer merely for scale. Add reconciliation because billing and fraud corrections require auditability. If reports are operational rather than financial, a pure Kappa architecture—replaying Kafka or S3 through one stream pipeline—may be sufficient.

04 / INGESTION

Keep the request path short

POST /v1/clicks
{
  "event_id": "0199a3c8-...",
  "ad_id": "ad_842",
  "campaign_id": "cmp_17",
  "clicked_at": "2026-09-12T19:42:17Z",
  "publisher_id": "pub_95",
  "country": "US",
  "device": "mobile"
}

202 Accepted
{ "event_id": "0199a3c8-...", "status": "queued" }
  1. Authenticate and rate-limit. Validate the publisher credential, request size, timestamp skew, and schema.
  2. Enrich minimally. Add server receipt time, coarse IP-derived geography, schema version, and trace ID.
  3. Append durably. Acknowledge only after the replicated event log confirms the write.
  4. Process asynchronously. Fraud checks and aggregation stay off the latency-sensitive request path.

Publish the event to a Kafka topic keyed by a stable hash of campaign_id. Kafka preserves order within each partition while distributing traffic. Large campaigns can use a composite key such as campaign_id + shard_id.

05 / STREAM PROCESSING

Aggregate in event-time windows

A Flink job consumes Kafka clicks, performs initial fraud filtering, deduplicates by event_id, and maintains one-minute tumbling windows. Event time—not arrival time—keeps a delayed mobile click in the correct reporting period.

Late data policy: configure Flink watermarks and allowed lateness to keep windows mutable for 10 minutes. Events later than that go to a side output and correction topic, then are folded in by reconciliation.

Deduplication in Flink

Key the stream by event_id and store a “seen” marker in Flink keyed state. On the first event, emit the click and register state with a TTL longer than the client retry and lateness window. Drop subsequent events while that marker exists. RocksDB-backed state keeps large deduplication sets off the JVM heap, while checkpoints persist state and Kafka offsets together. 

clicks
  .keyBy(event_id)
  .process(DeduplicateWithTTL)
  .keyBy(campaign_id, ad_id, shard)
  .window(TumblingEventTimeWindows.of(1 minute))
  .aggregate(ClickCount)

Flink checkpointing prevents duplicate state transitions during recovery, but end-to-end exactly-once still depends on the sink. Use idempotent ClickHouse writes with deterministic batch IDs or a transactional staging-and-commit pattern.

Rollups

Write low-cardinality, mergeable rows rather than incrementing one database counter per click. Minute buckets can later roll up into hour and day buckets. 

aggregate key:
  (minute, campaign_id, ad_id, country, device, shard)

measures:
  click_count, valid_click_count, estimated_cost

merge:
  SUM(measures) grouped by requested dimensions

The extra shard dimension spreads hot campaigns across workers. Queries sum the shards, trading a small amount of read work for much better write distribution.

07 / SEMANTICS

Design for retries and disagreement

Deduplication

Clients generate globally unique event IDs. Flink keeps partitioned keyed state with a TTL longer than the normal retry window. Sink writes use deterministic bucket and batch keys or idempotent upserts. A probabilistic filter can reduce lookups, but it must not be the only billing deduplicator because false positives would discard legitimate revenue events.

Replay

Flink checkpoints Kafka offsets and operator state together. After a failure, processing resumes from the last successful checkpoint. For code bugs, run the same versioned job against bounded Parquet input from S3, write to versioned aggregate tables, validate totals, then atomically switch the query layer.

Reconciliation

A daily Flink batch job recomputes closed periods from immutable Parquet events in S3, compares results against stream aggregates, and emits adjustments. Dashboards are provisional; reconciled rows are marked final and become the source for invoices.

Optimize for availability

Collection accepts traffic during downstream degradation because the log absorbs pressure.

Never hide uncertainty

Expose freshness and finalization state so consumers know whether totals may still change.

08 / BOTTLENECKS

Scale by partition, then isolate skew

  • Ingest API: stateless instances behind regional load balancers; autoscale on request rate and queue latency.
  • Kafka: add partitions for throughput, use a replication factor of at least three across availability zones, and alert on consumer lag.
  • Flink: use RocksDB-backed keyed state with durable S3 checkpoints; rescale job parallelism during low-traffic periods.
  • Hot campaigns: split one campaign across deterministic sub-shards and merge at query time.
  • ClickHouse: partition by date, distribute by campaign hash, and order by common filter dimensions.
  • Regions: ingest locally and aggregate regionally; merge global reports asynchronously to avoid cross-region latency on every click.
Backpressure must propagate to the event log, not to users. If processing falls behind, autoscale consumers and degrade dashboard freshness while keeping click collection available.
09 / PRODUCTION

Observe business truth, not just servers

System signals

  • Ingest success and p99 latency
  • Partition throughput and consumer lag
  • Checkpoint duration and failures
  • Query latency and rejected queries

Data-quality signals

  • Duplicate and invalid-event rate
  • Late-event distribution
  • Raw-to-aggregate count delta
  • Spend anomalies by campaign

Define a freshness SLO: 99% of valid clicks appear in advertiser reports within 60 seconds. Track it using synthetic clicks that traverse the complete pipeline, not merely component health checks.

Final design summary

Kafka decouples ingestion from computation. Stateful Flink jobs create fast, provisional aggregates. S3 and Parquet enable replay, audit, and correct billing. ClickHouse serves flexible reports, while idempotency and reconciliation make at-least-once infrastructure behave exactly once at the business level. This streaming-first, Lambda-inspired design preserves a truth path without requiring two unrelated implementations.
