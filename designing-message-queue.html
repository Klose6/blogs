Designing a Message Queue

Partitioned logs Visibility leases At-least-once 15 min read

How do we accept messages durably, deliver them to workers under bursty load, and recover when consumers fail halfway through processing? The design combines replicated append-only logs with leased delivery state.

01 / SCOPE

Decouple producers from consumers

Producers send messages to named queues. Consumer groups receive, process, and acknowledge them. The queue absorbs bursts, retries abandoned work, exposes backlog, and supports delayed delivery, priorities, retention, and dead-letter handling.

Functional

  • Send, batch-send, receive, acknowledge, and reject
  • Visibility timeout and lease extension
  • Delayed delivery, retry policy, and dead-letter queues
  • FIFO message groups and standard high-throughput queues

Non-functional

  • No acknowledged producer write silently lost
  • At-least-once consumer delivery
  • Millions of messages per second across queues
  • Availability through broker and zone failure
Scope distinction: a task queue removes or hides work as consumers acknowledge it. A replayable event stream keeps an immutable history and tracks offsets per subscriber. The storage can be similar, but retention and delivery semantics differ.
02 / CAPACITY

Plan for burst rate and retained bytes

Broker limits are driven by network and sequential disk bandwidth, while queue count and inflight leases drive metadata memory. Large payloads belong in object storage; messages should carry an immutable reference and checksum rather than multi-megabyte bodies.

03 / CONTRACT

Choose delivery guarantees explicitly

GuaranteeBehaviorTrade-off
At most once Remove before processing or never retry No duplicates, but crashes lose messages
At least once Retry until a valid acknowledgement arrives No silent loss, but handlers see duplicates
Exactly once Coordinate queue state and business side effects Possible only within a shared transaction boundary

This design guarantees at-least-once delivery. Every message carries a stable producer ID and idempotency key. Consumers record (consumer_name, message_id) in the same transaction as their business effect when duplicate effects are unacceptable.

Pull with long polling

Consumers issue a receive request that waits up to 20 seconds for a batch. Pull naturally expresses consumer capacity, simplifies firewalls, and supports backpressure. A streaming gRPC receive call can reduce request overhead while preserving consumer flow control.

04 / HIGH LEVEL

Separate control, storage, and delivery state

Partition leaders replicate append-only segments before acknowledging; delivery coordinators lease committed entries to consumer groups.

05 / STORAGE

Use append-only segments plus compact state

MessageRecord {
  queue_id
  partition_id
  offset
  message_id
  producer_id
  idempotency_key
  available_at
  priority
  payload_or_blob_ref
  checksum
  created_at
}

Each partition is a replicated append-only log split into immutable segment files. Sequential writes maximize disk throughput. A sparse offset index locates records; checksums detect corruption. Active segment tails and indexes remain in page cache.

Per consumer group, maintain a compact acknowledgement bitmap or range set, an inflight lease table, and a ready cursor. A segment can be deleted when every required group has acknowledged it and the retention floor has passed. Old retained segments may move to S3.

Do not rewrite a message to update its state. Message bytes remain immutable. Acknowledgements, leases, retries, and dead-letter transitions are small replicated state records that reference the original offset.
06 / PRODUCERS

Acknowledge only after quorum persistence

  1. Authenticate and validate. Enforce queue ACL, producer quota, payload limit, schema, and retention policy.
  2. Choose a partition. Hash the ordering key when supplied; otherwise use a load-aware round-robin partitioner.
  3. Deduplicate. The leader remembers recent producer sequence numbers or idempotency keys within a bounded window.
  4. Append and replicate. Write the record to the leader log and replicate it to followers in other zones.
  5. Commit and respond. After a quorum persists the record, return message ID, partition, and offset. 
POST /v1/queues/email/messages
Idempotency-Key: 0199fa2e-...
{
  "group_key": "customer_842",
  "delay_seconds": 0,
  "payload": { "template": "receipt", "order_id": "ord_17" }
}

Batch adjacent messages into one request and one disk flush. Apply producer backpressure before broker memory fills: reject with a retryable error or block within a strict deadline when quotas, replication lag, or disk latency exceed safe bounds.

07 / CONSUMERS

Lease messages with receipt tokens

  1. A consumer long-polls with group name, batch size, and maximum processing time.
  2. The coordinator chooses visible committed messages and atomically records leases with deadlines and random receipt tokens.
  3. The consumer processes each message and acknowledges using the current receipt token—not only the message ID.
  4. A valid acknowledgement marks the group offset complete. A stale token from an expired worker is rejected.
  5. An expired lease increments delivery count and returns the message to ready state or schedules a retry. 
ReceiveResponse {
  message_id: "msg_..."
  receipt_token: "random-per-delivery-token"
  delivery_count: 3
  lease_until: "2026-09-22T22:15:30Z"
  payload: ...
}

Workers may extend visibility before a long operation expires. Cap total lease duration so a stuck consumer cannot hide work forever. Deleting or acknowledging must be idempotent for the same valid token.

08 / ORDERING

Order by partition or message group

A partition leader assigns a total append order. With several partitions, the queue has no global order. This is usually desirable: throughput scales with partitions and unrelated work proceeds independently.

Standard queue

Deliver any visible message. Retries may reorder work, maximizing throughput and availability.

FIFO message groups

Hash each group to one partition and allow only one inflight message per group. Different groups still run in parallel.

Strict queue-wide FIFO requires one partition and one inflight message, turning the queue into a bottleneck. Expose ordering groups so callers pay serialization only where business semantics require it.

09 / POISON WORK

Retry without blocking healthy messages

On explicit failure or lease expiry, calculate exponential backoff with full jitter and place the offset into the delayed-delivery index. Other messages continue even if one item repeatedly fails. 

delay = random(0, min(max_delay, base × 2^delivery_count))

After the configured attempt count or a permanent error, atomically append a dead-letter envelope containing the original queue, offset, failure reason, and delivery history. Mark the original terminal for that consumer group only after the DLQ append commits.

Redrive creates a new delivery attempt while preserving the original message ID and idempotency identity. Operators can filter by error class and task version instead of replaying every poison message.

10 / TIME

Index future availability separately

Keep messages delayed for hours or days in a durable due-time index partitioned by minute and shard. Coordinators prefetch a short horizon into an in-memory hierarchical timing wheel. When due, an offset becomes visible in its queue partition.

This avoids scanning the entire log for available_at ≤ now and prevents long-delay timers from consuming broker heap. The wheel is disposable; after restart it rebuilds from durable time buckets with an overlap window so no due item is skipped.

Priority queues maintain a small number of classes—such as urgent, normal, and bulk—rather than an unbounded numeric heap. Weighted scheduling prevents bulk starvation while reserving capacity for urgent traffic.

11 / RECOVERY

Make broker and consumer crashes ordinary

FailureRecovery
Leader fails before quorum commitProducer retries; new leader discards uncommitted tail
Leader fails after commit, before responseProducer retries same idempotency key and receives original result
Consumer dies during processingVisibility lease expires and another consumer receives the message
Acknowledgement response is lostDuplicate delivery occurs; consumer idempotency suppresses duplicate effects
Disk corruptionChecksum fails, replica is quarantined, and segment is copied from a healthy peer

Metadata controllers use Raft for queue definitions, partition assignments, replica epochs, ACLs, and quotas. Data partitions use their own replication groups, so a control-plane leader failure does not stop already-routed produce and consume traffic.

Rebalancing

Add a follower on the target broker, stream immutable segments, catch up the active tail, then transfer leadership with a higher epoch. Remove the old replica only after the new set is healthy. Rate-limit movement to protect foreground latency.

12 / MULTI-REGION

Give each queue a home region

Replicate synchronously across availability zones inside one home region. Cross-region quorum writes add large latency and sacrifice availability during partitions. Mirror committed segments and queue metadata asynchronously to a disaster-recovery region.

Regional task queues

Producers target the queue nearest its workers. Applications create separate queues when work may execute independently by region.

Global ordered queue

Route all writes for an ordering key to one home region and accept the extra network hop. Do not merge independent leaders.

Disaster failover fences the previous region, promotes a known replicated offset, and reissues inflight messages because lease state may be stale. At-least-once semantics make those duplicates expected.

Prefer a mature managed system unless custom queue semantics, isolation, or economics justify building brokers. The architecture here explains the mechanisms behind those systems; it is not a reason to replace them casually.

Production signals

  • Produce, visible-to-receive, and end-to-end acknowledgement latency
  • Ready, inflight, delayed, retried, and dead-letter message counts
  • Partition skew, replica lag, quorum health, and leader elections
  • Consumer utilization, lease expiry, duplicate delivery, and redrive rate
  • Disk utilization, flush latency, segment corruption, and tiering backlog
  • Quota rejection, payload size, and producer backpressure duration

Final design summary

Partition leaders append immutable message records and replicate them across zones before acknowledgement. Delivery coordinators lease committed offsets to long-polling consumers with receipt tokens. Expired leases create at-least-once retries; idempotency protects side effects. Timing wheels manage near-term delays, durable time buckets hold long delays, and poison messages move atomically to DLQs. Raft-replicated metadata, tiered segments, fenced failover, and home-region ownership keep the system scalable and recoverable.
