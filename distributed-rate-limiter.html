Designing a Distributed Rate Limiter

Token bucket Redis Low latency 12 min read

How do we enforce quotas across thousands of application servers without adding a fragile network hop to every request? The answer combines atomic shared state, local token leases, and explicit failure policies.

On this page Requirements Algorithm Architecture Request flow Data model Scaling Failure policy Multi-region Operations
01 / SCOPE

Protect systems and enforce plans

A rate limiter decides whether a request may proceed under one or more rules. It protects dependencies from overload, prevents abuse, and enforces customer quotas. It should be substantially faster and more available than the service it protects.

Functional

  • Limit by user, API key, IP, tenant, or route
  • Support steady rates with short bursts
  • Return remaining quota and retry timing
  • Update policies without application deploys

Non-functional

  • Decision latency below 5 ms at p99
  • Millions of decisions per second
  • No single point of failure
  • Bounded quota overshoot during failures
Semantics first: a rate limiter cannot maximize availability, global accuracy, and low latency during a network partition. Define whether each endpoint fails open or fails closed.
02 / ALGORITHM

Use a token bucket

Each key owns a bucket with capacity C. Tokens refill continuously at rate R per second. A request costing N tokens is allowed only when at least N tokens remain.

available = min(C, previous + elapsed_seconds × R)
allow = available ≥ cost

Capacity controls burst size; refill rate controls sustained traffic. A bucket with capacity 100 and refill rate 10/s allows an idle client to burst 100 requests, then sustain 10 requests/s.

Algorithm Strength Weakness
Fixed window Cheap counter and expiry Boundary bursts can reach 2× the limit
Sliding log Precise rolling window Stores one timestamp per request
Sliding counter Good accuracy and bounded state Approximation near boundaries
Token bucket O(1) state and natural bursts Requires atomic refill arithmetic

The control plane distributes rules; the data plane makes request decisions.

Data plane

Gateway-side agents load cached policies and evaluate requests. Shared counters live in a partitioned in-memory store.

Control plane

A policy service validates, versions, and distributes rules. Its outage must not stop decisions using the last known policy.

A sidecar or library avoids an extra service hop, but complicates upgrades. A dedicated service centralizes logic, but adds latency and another availability dependency. A gateway plugin is often the best fit when most traffic already crosses a gateway.

04 / DECISION PATH

Make one atomic decision

  1. Build a descriptor. Extract trusted identity, route, method, and cost into a canonical rule key.
  2. Resolve policy locally. Match the descriptor against a versioned in-memory policy cache.
  3. Consume tokens atomically. Route the key to its owner shard and run refill-and-consume as one operation.
  4. Return the decision. Allow the request or return HTTP 429 with standard rate-limit and retry headers. 
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 7
Retry-After: 7

Never trust a client-supplied user ID or IP header directly. Identity must come from authenticated claims or a trusted proxy; otherwise callers can rotate keys and bypass the limit.

05 / STATE

Keep state compact and atomic

policy:
  id: "tenant-write-v3"
  match: { route: "/v1/orders", method: "POST" }
  key_by: ["tenant_id"]
  capacity: 100
  refill_per_second: 10
  request_cost: 1
  failure_mode: "closed"

bucket key:
  rl:{tenant-write-v3}:{tenant_842}

bucket value:
  tokens: 67.4
  last_refill_ms: 1789252937000

In Redis, use a Lua script or server-side function so reading the timestamp, calculating refill, consuming tokens, updating state, and setting expiry happen atomically. Use the datastore's clock to avoid inconsistent application-server clocks.

Expire idle buckets: a bucket can be deleted after enough time has passed to refill it completely. On the next request, absence means a full bucket. This bounds memory by active keys.

Hierarchical limits

A request may consume from user, tenant, route, and global buckets. Checking them independently can partially consume quota before a later rule rejects the request. Co-locate related keys with hash tags and update all buckets atomically, or reserve and compensate with carefully designed idempotency.

06 / THROUGHPUT

Lease tokens to reduce network traffic

One shared-store operation per application request eventually becomes expensive. Instead, each gateway leases a small batch of tokens from the global bucket and spends them locally.

10–100×

fewer remote calls

One lease supports a batch of local decisions.

<1 ms

common-path latency

Most decisions use process-local memory.

bounded

quota overshoot

At most outstanding leases across live gateways.

Choose lease size dynamically. High-volume stable keys receive larger leases; low-volume or security-sensitive keys use smaller leases or direct checks. Short lease TTLs bound stranded capacity when an agent crashes.

Partitioning

Consistent-hash bucket keys across state-store shards and replicate each shard across availability zones. One celebrity tenant can still create a hot key because a single bucket has one owner. Mitigate it with token leasing, per-gateway sub-buckets, or a two-level local-plus-global policy.

07 / FAILURE POLICY

Failure behavior is a product decision

Endpoint type Suggested behavior Reason
Public read API Fail open with local emergency limit Preserve availability while containing overload
Login or password reset Fail closed Abuse prevention is more important than availability
Paid usage quota Fail closed or use a bounded lease Avoid unbilled usage and contractual violations
Internal health check Bypass Do not make recovery depend on the limiter

Add strict timeouts and a circuit breaker around the shared store. If it slows down, do not allow limiter calls to exhaust gateway threads. The agent should switch immediately to the configured degraded mode and emit a high-severity signal.

Policy service outage

Persist the last known valid policy snapshot locally. Policies carry versions and activation times, and invalid updates are rejected atomically. The decision path never synchronously calls the policy service.

08 / GLOBAL LIMITS

Avoid a cross-ocean decision hop

A strongly consistent global counter adds inter-region latency and loses availability during partitions. Most products should divide quota among regions and enforce each allocation locally.

Example: for a global limit of 10,000 requests/s, allocate 5,000 to the US, 3,000 to Europe, and 2,000 to Asia. Rebalance allocations periodically as demand moves.

Keep a reserve pool so a busy region can acquire more capacity. During a partition, each region can overshoot only by its local allocation or outstanding lease. If strict global enforcement is mandatory, route all requests for a key to a home region and accept the latency and availability cost.

09 / PRODUCTION

Measure protection and user impact

Service health

  • Decision latency by outcome and shard
  • State-store errors and timeouts
  • Policy age and distribution lag
  • Lease utilization and stranded tokens

Business health

  • Allow and reject rate by policy
  • Top rejected tenants and routes
  • Time spent in degraded mode
  • Estimated overshoot and false rejects

Log sampled decisions with policy version, key hash, outcome, and remaining quota—but never raw API keys or sensitive identity. Provide a dry-run mode so new policies report what they would block before they begin enforcing.

Final design summary

Use token buckets for constant-size state and controlled bursts. Evaluate cached policies at the gateway, perform atomic updates in a sharded in-memory store, and lease tokens locally at scale. Separate policy management from request decisions, allocate global quota regionally, and define explicit fail-open or fail-closed behavior for every rule.
