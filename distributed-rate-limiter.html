Designing a Distributed Rate Limiter

Token bucket Redis Low latency 12 min read

How do we enforce quotas across thousands of application servers without adding a fragile network hop to every request? The answer combines atomic shared state, local token leases, and explicit failure policies.

On this page Requirements Algorithm Architecture Request flow Data model Scaling Failure policy Multi-region Operations
01 / SCOPE

Protect systems and enforce plans

A rate limiter decides whether a request may proceed under one or more rules. It protects dependencies from overload, prevents abuse, and enforces customer quotas. It should be substantially faster and more available than the service it protects.

Functional

  • Limit by user, API key, IP, tenant, or route
  • Support steady rates with short bursts
  • Return remaining quota and retry timing
  • Update policies without application deploys

Non-functional

  • Decision latency below 5 ms at p99
  • Millions of decisions per second
  • No single point of failure
  • Bounded quota overshoot during failures
Semantics first: a rate limiter cannot maximize availability, global accuracy, and low latency during a network partition. Define whether each endpoint fails open or fails closed.
02 / ALGORITHM

Compare the algorithms

Rate-limiting algorithms mainly differ in how they represent time and whether they permit bursts. Assume every example below has a limit of 100 requests per minute.

Algorithm Strength Weakness
Fixed window Cheap counter and expiry Boundary bursts can reach 2× the limit
Sliding log Precise rolling window Stores one timestamp per request
Sliding counter Good accuracy and bounded state Approximation near boundaries
Token bucket O(1) state and natural bursts Requires atomic refill arithmetic
Leaky bucket Smooth, predictable output rate Queues requests and may add latency

Fixed window counter

Divide time into separate windows—such as 12:00–12:01—and keep one counter per key. Increment the counter on every request and reject after it reaches 100. When 12:01 begins, reset it.

It is simple and memory-efficient, but a client can send 100 requests at 12:00:59 and another 100 at 12:01:00. The system sees 200 requests in two seconds while each window remains valid.

Sliding window log

Store the timestamp of every accepted request. For a request at 12:01:30, delete timestamps older than 12:00:30 and count what remains. Reject when there are already 100 entries.

This gives an exact rolling-minute limit and removes the boundary burst. However, a busy key needs up to 100 stored timestamps, making memory and cleanup work grow with the limit.

Sliding window counter

Keep only the current and previous fixed-window counters, then weight the previous one by how much of it overlaps the last minute. Halfway through a window, the estimate is current + 0.5 × previous.

It uses constant memory and is much smoother than a fixed window. Because it estimates when requests happened inside the previous window, it can allow or reject a few requests incorrectly.

Token bucket

Imagine a bucket that holds 100 tokens and refills continuously. Each request removes one token; an empty bucket rejects the request. Idle time fills the bucket and creates burst capacity.

Capacity controls the maximum burst, while refill rate controls sustained traffic. It needs only the token balance and last refill time, making it the best default for this service.

Leaky bucket

Think of requests entering a queue that drains at a constant rate, like water leaving a bucket through a small hole. If the queue is full, new requests are rejected.

It turns bursty input into smooth output, which is useful for protecting a slow worker. Unlike token bucket, it delays queued requests, so it is less suitable for a gateway that must decide immediately.

Why this design chooses token bucket

API clients often need short bursts—for example, loading a page may trigger several requests at once—but should still obey a long-term quota. Token bucket models that behavior directly and keeps only constant-size state per active key.

available = min(C, previous + elapsed_seconds × R)
allow = available ≥ request_cost

A bucket with capacity 100 and refill rate 10 tokens/s lets an idle client burst up to 100 requests, then sustain 10 requests/s. Requests may have different costs: a cheap read can consume one token while an expensive report consumes ten.

03 / HIGH LEVEL

Put enforcement close to traffic

The request path branches at Envoy: allowed traffic reaches the upstream API, while quota checks use the data plane below it.

Data plane

Envoy calls a nearby Go rate-limit service over gRPC. The service caches policies and stores shared counters in Redis.

Control plane

A Go policy API stores versioned rules in PostgreSQL and pushes updates to limiter instances. Its outage does not stop decisions.

A sidecar or library avoids an extra service hop, but complicates upgrades. A dedicated service centralizes logic, but adds latency and another availability dependency. Envoy's standard gRPC rate-limit filter gives us centralized behavior while keeping the service independently scalable and close to each gateway.

Recommended technology stack

Responsibility Tool Why it fits
Traffic enforcement Envoy Gateway Extracts trusted descriptors, calls a gRPC limiter, and returns HTTP 429 before upstream work begins
Decision service Go + gRPC Low allocation overhead, predictable latency, and compatibility with Envoy's rate-limit service API
Bucket state Redis Cluster 7 Sub-millisecond in-memory access, sharding, expiry, and atomic Redis Functions
Policy storage PostgreSQL Transactional policy versions, audit history, and safe configuration updates
Deployment Kubernetes Runs one limiter deployment per region and autoscales it independently from gateways
Telemetry Prometheus + Grafana Low-cardinality metrics, SLO dashboards, and alerts for latency or degraded mode
Managed deployment: on AWS, use EKS for Envoy and the Go services, ElastiCache for Redis in cluster mode, and RDS for PostgreSQL. Equivalent managed products work on other clouds; the Redis and gRPC interfaces keep the design portable.
04 / DECISION PATH

Make one atomic decision

  1. Build an Envoy descriptor. Extract trusted identity, route, method, and cost into a canonical rule key.
  2. Call the Go service. Envoy uses a short-lived HTTP/2 gRPC request to a limiter instance in the same zone.
  3. Consume tokens atomically. The service resolves its cached policy and invokes a Redis Function on the owner shard.
  4. Return the decision. Envoy allows the request or returns HTTP 429 with standard rate-limit and retry headers. 
HTTP/1.1 429 Too Many Requests
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 7
Retry-After: 7

Never trust a client-supplied user ID or IP header directly. Identity must come from authenticated claims or a trusted proxy; otherwise callers can rotate keys and bypass the limit.

05 / STATE

Keep state compact and atomic

policy:
  id: "tenant-write-v3"
  match: { route: "/v1/orders", method: "POST" }
  key_by: ["tenant_id"]
  capacity: 100
  refill_per_second: 10
  request_cost: 1
  failure_mode: "closed"

bucket key:
  rl:{tenant-write-v3}:{tenant_842}

bucket value:
  tokens: 67.4
  last_refill_ms: 1789252937000

In Redis 7, deploy a versioned Redis Function that reads the server clock, calculates refill, consumes tokens, updates state, and sets expiry atomically. Prefer Functions over sending ad hoc Lua on every request: they are named, loaded once, and easier to version operationally. 

-- Redis Function, simplified token-bucket operation
local now = redis.call("TIME")
local state = redis.call("HMGET", key, "tokens", "refilled_at")
local available = math.min(capacity, tokens + elapsed * refill_rate)

if available < cost then
  return { 0, available, retry_after_ms }
end

redis.call("HSET", key,
  "tokens", available - cost,
  "refilled_at", now_ms)
redis.call("PEXPIRE", key, ttl_ms)
return { 1, available - cost, 0 }
Expire idle buckets: a bucket can be deleted after enough time has passed to refill it completely. On the next request, absence means a full bucket. This bounds memory by active keys.

Hierarchical limits

A request may consume from user, tenant, route, and global buckets. Checking them independently can partially consume quota before a later rule rejects the request. Co-locate related keys with hash tags and update all buckets atomically, or reserve and compensate with carefully designed idempotency.

06 / THROUGHPUT

Lease tokens to reduce network traffic

One shared-store operation per application request eventually becomes expensive. Instead, each Go limiter instance leases a small batch of tokens from the global Redis bucket and spends them from an in-process cache.

10–100×

fewer remote calls

One lease supports a batch of local decisions.

<1 ms

common-path latency

Most decisions use process-local memory.

bounded

quota overshoot

At most outstanding leases across live limiter instances.

Choose lease size dynamically. High-volume stable keys receive larger leases; low-volume or security-sensitive keys use smaller leases or direct checks. Short lease TTLs bound stranded capacity when an agent crashes.

Partitioning

Redis Cluster hashes bucket keys across primary shards; place each primary and replica in different availability zones. One celebrity tenant can still create a hot key because a single bucket has one owner. Mitigate it with token leasing, per-instance sub-buckets, or a two-level local-plus-global policy.

07 / FAILURE POLICY

Failure behavior is a product decision

Endpoint type Suggested behavior Reason
Public read API Fail open with local emergency limit Preserve availability while containing overload
Login or password reset Fail closed Abuse prevention is more important than availability
Paid usage quota Fail closed or use a bounded lease Avoid unbilled usage and contractual violations
Internal health check Bypass Do not make recovery depend on the limiter

Configure Envoy with a 5 ms gRPC timeout and circuit breaking for the limiter cluster. The Go service uses a shorter Redis timeout so it can still return a policy-specific degraded decision. For total gRPC service failure, configure security-sensitive Envoy routes with failure_mode_deny; fail-open routes pair the external limiter with Envoy's local rate-limit filter as an emergency ceiling.

Policy service outage

Each Go limiter persists the last valid PostgreSQL policy snapshot on local disk and keeps it in memory. Policies carry versions and activation times, and invalid updates are rejected atomically. The decision path never synchronously calls PostgreSQL or the policy API.

08 / GLOBAL LIMITS

Avoid a cross-ocean decision hop

A strongly consistent global counter adds inter-region latency and loses availability during partitions. Most products should divide quota among regions and enforce each allocation locally.

Example: for a global limit of 10,000 requests/s, allocate 5,000 to the US, 3,000 to Europe, and 2,000 to Asia. Rebalance allocations periodically as demand moves.

Keep a reserve pool so a busy region can acquire more capacity. During a partition, each region can overshoot only by its local allocation or outstanding lease. If strict global enforcement is mandatory, route all requests for a key to a home region and accept the latency and availability cost.

09 / PRODUCTION

Measure protection and user impact

Service health

  • Prometheus decision latency by outcome and shard
  • Redis errors, saturation, and timeouts
  • Policy age and distribution lag
  • Lease utilization and stranded tokens

Business health

  • Allow and reject rate by policy
  • Top rejected tenants and routes
  • Time spent in degraded mode
  • Estimated overshoot and false rejects

Log sampled decisions with policy version, key hash, outcome, and remaining quota—but never raw API keys or sensitive identity. Export traces with OpenTelemetry and send structured logs to the existing log platform. Provide a dry-run mode so new policies report what they would block before they begin enforcing.

Final design summary

Envoy enforces decisions at the gateway and calls a Go gRPC limiter. Redis Cluster stores token buckets with atomic Redis Functions, while PostgreSQL stores versioned policies outside the request path. Local token leases reduce Redis traffic at scale. Kubernetes runs the stack per region, and Prometheus plus Grafana expose latency, rejections, and degraded behavior. Every rule still needs an explicit fail-open or fail-closed policy.
