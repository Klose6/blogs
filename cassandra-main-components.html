Cassandra Main Components

A Cassandra node keeps its own commit log, memtable, and SSTables. It learns who else is in the ring, and what the schema is, through gossip. Row bytes move only when a coordinator sends a mutation or a read, or when streaming copies a range for bootstrap or repair.

1. The Mental Model

Split the system at the replica boundary. Inside one node, a write is durable once it is in the commit log and visible once it is in the memtable. The SSTable is a later, sorted copy of that memtable. Compaction rewrites those files. Reads merge the memtable with whichever SSTables still cover the partition.

Outside the node, StorageProxy is the coordinator. It asks TokenMetadata who owns the token, then uses messaging to reach those replicas. Gossip is the channel that keeps that membership table, and the schema version, up to date. Gossip does not carry the rows.

The handoff to remember: the client ack is the commit log plus the memtable, on enough replicas for the consistency level. Flush, compaction, bootstrap streaming, and repair all happen against SSTables after that ack.

Coordinator

StorageProxy turns CQL into a mutation or a read, picks replicas, and waits for the consistency level. The write timestamp is the coordinator clock unless the statement sets one.

Ring

TokenMetadata is the in-memory ring. A node stores the tokens it owns. The range it serves is derived from its predecessor. NetworkTopologyStrategy fills each datacenter from nodes in that datacenter.

Local storage

CommitLog, then the memtable, then SSTables published through the table View. The trie memtable finds a partition. The rows inside that partition live in a B-tree.

Cluster metadata

Gossip carries status, tokens, and a schema version UUID. A mismatched UUID makes the node pull system_schema mutations from a member that already has that version.

2. Component Map

Every path in the rest of this article is one of these edges. Writes and reads enter through the coordinator. The replica apply path is commit log then memtable. Flush is the edge from the memtable into the SSTable set that compaction and reads share. Gossip feeds tokens and schema from the side. Bootstrap and repair reuse messaging to stream ranges that already exist on some other node.

  1. Client to StorageProxy

    CQL becomes a mutation or a read command. The coordinator owns the consistency level and, for a write, the timestamp.

  2. StorageProxy to TokenMetadata

    Replica choice uses the partition token and the keyspace strategy. With NetworkTopologyStrategy, each datacenter fills its replication factor from nodes in that datacenter, walking one shared ring.

  3. StorageProxy to messaging

    The mutation or the read is sent to those replicas. A typical read asks one replica for the rows and the others for a digest.

  4. Replica apply

    Keyspace.apply appends the mutation to the commit log, then puts the partition update in the current memtable. That is the point at which the replica can ack.

  5. Memtable to SSTable

    Flush writes the frozen memtable in token order and publishes a new SSTable in the table View. The commitlog segment can be discarded once no memtable still depends on it.

  6. SSTable to reads and compaction

    A point read searches the View interval tree. Compaction replaces files in that same view. Both paths see one table's live SSTables, not the whole keyspace.

  7. Gossip to the ring and the schema

    Endpoint state carries status, tokens, and ApplicationState.SCHEMA. The schema value is a UUID. The CREATE TABLE text arrives later, as a schema pull.

  8. Streaming for bootstrap and repair

    Both features copy existing SSTable ranges over messaging. They do not replay those rows through the coordinator write path.

3. Write Path

A write is finished for the client when enough replicas have the mutation in the commit log and the memtable. The SSTable does not exist yet. Flush is a local background step that runs because a memtable or the commit log crossed a threshold, or because something asked for a flush.

  1. Build the mutation

    QueryProcessor turns the statement into a Mutation. The timestamp is the coordinator's clock unless the query uses USING TIMESTAMP. Last-write-wins is this timestamp, compared per cell.

  2. Choose replicas and send

    StorageProxy.mutate resolves natural replicas for the token and sends the mutation. The coordinator returns when the consistency level is satisfied. A down replica can be covered by a hint stored on the coordinator and replayed inside the hint window.

  3. Append the commit log

    On the replica, CassandraKeyspaceWriteHandler calls CommitLog.instance.add before the memtable accepts the update. Tables whose memtable factory skips the commit log are left out of that append.

  4. Put the partition in the memtable

    ColumnFamilyStore.apply calls Memtable.checkSpaceAndPut. In the trie memtable the path is the decorated partition key: token bytes, then key bytes. The rows for that partition sit in a B-tree, merged by clustering key. A later write to the same partition updates that B-tree. The trie does not store the row cells.

  5. Ack, then flush on a later cycle

    The replica acks. The client is done. Flush calls switchMemtable, writes the frozen memtable as a sorted SSTable, publishes it in the View, and submits background compaction.

4. Read Path

One replica builds the merged partition. The other replicas contacted for the consistency level usually return a digest of that same result. The coordinator returns the data response when the digest matches. Tombstones are scanned on the replica even when the bytes sent back to the coordinator are small.

  1. Build the read and pick replicas

    StorageProxy.fetchRows creates an AbstractReadExecutor per command. Replicas come from TokenMetadata and are ordered by the snitch. The table parameter speculative_retry defaults to 99PERCENTILE, so a slow first wave can trigger one extra request.

  2. Send data to one replica and digests to the others

    The closest replica is asked for the rows. The other replicas required by the consistency level are asked for a digest. Local read size on the data replica includes tombstones. Coordinator read size counts the serialized result.

  3. Select SSTables, then probe each file

    SinglePartitionReadCommand reads the memtable and calls View.select for the partition key. The interval tree returns SSTables whose first and last keys cover that partition. Under leveled compaction that is the overlapping L0 files and at most one file per higher level. Each candidate is checked with its own bloom filter, the key cache, and its own index summary. The summary points at one interval of the primary index, and that interval points into the data file.

  4. Merge cells

    Iterators from the memtable and the SSTables are merged. Cells.resolveRegular keeps the cell with the higher timestamp. An equal timestamp keeps a tombstone over a live value. LIMIT counts live rows, so dead rows are still walked until the limit is filled or the partition ends. A partition tombstone newer than an SSTable's maximum timestamp can skip that file. A range tombstone is two markers around a clustering slice, and it does not skip a file that still has live rows outside the slice.

  5. Compare digests and return

    The coordinator returns the data response when the digests agree. A mismatch reads full data from the replicas and repairs the stale copies. The scan cost of tombstones stays on the replica that built the merge.

5. Compaction

Compaction rewrites SSTables the node already owns. In Cassandra 5.0 the unified strategy groups files by density, then by how much their token ranges overlap. A bucket is work when that overlap passes a threshold derived from the scaling parameter W. The pending-task metric is that estimate plus compactions already running. It is refreshed when the strategy is asked for the next task.

  1. Something publishes an SSTable

    A flush, or a compaction that just finished, calls CompactionManager.submitBackground for that table.

  2. Ask the strategy, repair files first

    CompactionStrategyManager.getNextBackgroundTask considers promotion or demotion of pending-repair SSTables before an ordinary compaction.

  3. Pick a bucket

    UnifiedCompactionStrategy sorts SSTables into levels by density, which is size divided by token span. Inside a level, files form overlap buckets. W below zero behaves like leveled compaction, zero is the neutral fanout, and above zero behaves like tiered compaction. The chosen bucket is the one whose overlap is past the threshold.

  4. Merge and write shards

    CompactionTask merges the picked files with a CompactionIterator, resolving cells and tombstones the same way a read does. ShardedCompactionWriter starts a new output SSTable when the token crosses a shard boundary.

  5. Swap the view and look again

    The tracker drops the inputs and publishes the outputs. If a task ran, background compaction is submitted again.

Why the lag number moves: estimatedRemainingTasks adds each bucket's overlap divided by the threshold. Compaction.PendingTasks reports that sum plus compactions already running. A table that is falling behind shows a larger overlap, so the estimate climbs the next time the strategy is asked for work.

6. New Node Bootstrap

A new node starts from the seed list in cassandra.yaml. Seeds are the first gossip contact. From a seed the node learns the other members, their tokens, and each member's schema version. It pulls the schema, streams the ranges it will own, and then publishes NORMAL. Peers learn that the join finished on the next gossip exchange.

  1. Recover local disk first

    CassandraDaemon.setup loads system tables, replays the commit log, and calls Schema.loadFromDisk. A brand-new node has no user keyspaces, so its schema version will not match the cluster.

  2. Ask the seeds, once, before joining

    checkForEndpointCollision runs Gossiper.doShadowRound. An empty GOSSIP_DIGEST_SYN goes to every configured seed. The ack is the endpoint map that seed knows: peers, tokens, status, and schema version. That map is kept aside. It is used to reject an address collision and, by default, to reject the join while another node is bootstrapping, leaving, or moving. With num_tokens: 1 the same check still applies. Distance between the new tokens is not consulted.

  3. Start gossip, then learn the live set

    prepareToJoin calls Gossiper.start and then Schema.startSync. With no live endpoints yet, each gossip round contacts a seed. The seed's state includes the other members. Those members become the peers this node gossips with directly.

  4. Pull schema from a member that has the version

    MigrationCoordinator announces the local schema UUID. DefaultSchemaUpdateHandler records ApplicationState.SCHEMA from each live ring member. A different UUID schedules SCHEMA_PULL_REQ. The peer answers with SchemaKeyspace.convertSchemaToMutations(), and the joiner applies those mutations into its own system_schema tables. Any member that advertises the version can answer. A seed is simply one such member when it is already in the ring.

  5. Stream, then publish NORMAL

    waitForSchema blocks while the in-memory schema is empty and until the outstanding pulls finish. A non-seed with auto_bootstrap then allocates tokens and RangeStreamer copies the ranges it will own. With a single token, the node stores that token. The range it serves is (predecessor, token]. After streaming succeeds, setTokens writes system.local, marks the local node NORMAL, and gossip publishes TOKENS and STATUS NORMAL. The joining node decides success locally, from the streaming result and setTokens.

  6. Peers install the new member

    The next gossip version bump delivers NORMAL. StorageService.onChange calls handleStateNormal, which updates token metadata. From then on, coordinators can select the new node as a replica.

A single-token node stores its token, not a pair of range endpoints. The predecessor is computed from the current ring, so ownership changes when some other node joins or leaves in front of it.

7. Incremental Repair

Consistent incremental repair isolates the ranges under repair into their own SSTables, compares those files, streams the differences, and leaves a later compaction to mark them repaired. The repair session and the compaction strategy meet in the pendingRepair id on the SSTable.

  1. Open a session

    IncrementalRepairTask registers a CoordinatorSession and runs the repair with the incremental flag set.

  2. Prepare, then isolate the range

    Prepare asks each participant to join. PendingAntiCompaction then splits unrepaired SSTables that intersect the range. The in-range piece is marked pendingRepair with this session id. Files that are already repaired, and files that belong to another session, stay out.

  3. Validate and stream

    Validation reads only SSTables whose pendingRepair id is this session. The coordinator compares results. Ranges that disagree are streamed between the participants. Ranges that match move no row data.

  4. Promise, commit, then compact

    Finalize propose has each node persist FINALIZE_PROMISED and flush the repairs table before it acks. Finalize commit ends the session. The data files are still pending. incrementalSessionCompleted submits background compaction, and that later task promotes them to repaired. A failed session sends FailSession. Demotion of those pending files also happens later, in compaction.

Full repair is the other shape. It validates unrepaired data in the range and streams differences without a pendingRepair session, so there is no anti-compaction step and no later promotion.

8. Details Worth Keeping

These are the spots where the code is more specific than the one-line description of the feature.

Topic What this tree does
Write visibility The ack means commit log and memtable on enough replicas. The SSTable appears at flush.
Last write wins Resolution is per cell, by timestamp. Two writes to different columns of the same row both survive. Counters are summed.
Who sends rows One replica sends the merged read response. Other full replicas usually send a digest. A digest mismatch triggers a full read and read repair.
Tombstone latency LIMIT counts live rows. Dead cells, row deletions, and range-tombstone markers are still scanned, and TombstoneScannedHistogram records that count per read.
Point-read SSTables The interval tree returns candidates for that partition. Each candidate has its own bloom filter and index summary. L0 files usually overlap, so a point read checks most of L0.
Compaction lag Pending tasks are overlap divided by the unified-compaction threshold, plus tasks already running.
Schema on a new node Gossip delivers a schema UUID. SCHEMA_PULL_REQ fetches the system_schema mutations from a member with that version.
Join success The joining node marks itself NORMAL after streaming and setTokens. Peers apply that state from gossip.
Single token The node persists its token. The served range is (predecessor, token], computed from the current ring.
Two nodes joining With consistent range movement left on, a node refuses to bootstrap while any peer is already joining, leaving, or moving.
