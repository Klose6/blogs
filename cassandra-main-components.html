Cassandra Main Components

Think of a Cassandra cluster as many independent stores that copy the same partitions. Each node keeps its own commit log, memtable, and SSTables. Gossip tells it who else is in the ring. A coordinator asks those replicas to write, read, or agree on a compare-and-set. Streaming copies existing files when a node joins or when repair finds a gap.

1. The Mental Model

Cassandra is a partitioned wide-column store. A partition key hashes to a token. That token decides which nodes keep a copy. Inside one node, a write is durable in the commit log and readable from the memtable. An SSTable is a later, sorted copy of that memtable. A read merges the memtable with the SSTables that still cover the partition. Compaction rewrites those files so later reads have less to merge.

The node that received the client query is the coordinator. It looks up who owns the token, then uses messaging. Gossip keeps that membership table, and the schema version, up to date. Gossip does not carry row data.

The handoff to remember: a normal write is done for the client when enough replicas have it in the commit log and the memtable. Flush, compaction, bootstrap, and repair all work on SSTables after that ack. An LWT is different: the replicas first vote, then the same write path commits the winner.

Coordinator

Turns CQL into a mutation or a read, picks replicas, and waits for the consistency level. The write timestamp is this node's clock unless the statement sets one.

Ring

Each node stores the tokens it owns in system.local. Each token covers the ring from the previous token up through itself. With Network Topology Strategy, each datacenter fills its own copy count from nodes in that datacenter.

Local storage

Commit log, then memtable, then SSTables. The memtable finds a partition by key. The rows inside that partition live in a B-tree.

Cluster metadata

Gossip carries status, tokens, and a schema version. A mismatched version makes the node download the actual table definitions from a peer.

Consensus

An IF write is a lightweight transaction. Paxos asks a quorum of replicas to promise, propose, then commit. It only covers one partition.

Secondary indexes

SAI is a local index on each memtable and SSTable. Vector search is SAI on a vector column. The replica still reads the matching rows from its own data.

2. Component Map

The top row is how a request finds replicas. The bottom row is what one replica does with the bytes. StorageProxy asks TokenMetadata who owns the token, then MessagingService delivers the verb. On the replica, Keyspace.apply appends the commit log and then updates the memtable. Flush is the only arrow from the memtable to an SSTable. Gossip writes status, tokens, and a schema version into endpoint state. It does not call apply.

  1. Client to coordinator

    CQL becomes a mutation, a read, or an IF compare-and-set. The coordinator owns the consistency level and, for a normal write, the timestamp.

  2. Coordinator to the ring

    The partition token plus the keyspace strategy name the replicas. With Network Topology Strategy, each datacenter fills its own copy count from nodes in that datacenter. There is still one shared ring.

  3. Coordinator to messaging

    A normal write uses writeNormal, which contacts every natural and pending replica when the keyspace has no transient replicas. A typical read asks the first full contact for the rows and the other contacted full replicas for a digest. An LWT runs Paxos first, then commits through the same apply path.

  4. Replica apply

    The replica appends the mutation to the commit log, then puts it in the memtable. That is when it can ack. If SAI indexes the table, the memtable index is updated here too.

  5. Memtable to SSTable

    Flush writes the memtable in token order and publishes a new SSTable. The commit-log segment can be dropped once no memtable still needs it. SAI writes its index files next to that SSTable.

  6. SSTables to reads and compaction

    A point read asks the table's live-file set which SSTables cover this partition. Compaction replaces files in that same set. Both paths see one table, not the whole keyspace.

  7. Gossip to the ring and the schema

    Gossip carries status, tokens, and a schema version UUID. The CREATE TABLE text arrives later, as a schema pull from a peer that already has that version.

  8. Streaming for bootstrap and repair

    Both copy existing SSTable ranges over messaging. They do not replay those rows as new client writes.

3. Write Path

A normal write is finished for the client when enough replicas have the mutation in the commit log and the memtable. No SSTable has been written yet. Flush happens later, when a memtable or the commit log is full, or when someone asks for a flush.

  1. Build the mutation

    The statement becomes a mutation. The timestamp is the coordinator clock unless the query uses USING TIMESTAMP. Last-write-wins compares this timestamp on each cell, not on the whole row.

  2. Send to every replica, wait for enough acks

    performWrite uses ReplicaPlans.writeNormal. With no transient replicas, contacts is every natural and pending replica, up or down. sendToHintedReplicas delivers the mutation to each live one. The client returns when the consistency level is met, for example two of three for quorum. The other live replicas still get the write.

  3. If a replica is down, save a hint

    A down replica in that contact list gets a hint on the coordinator, replayed after it returns, while max_hint_window still allows it. Hints shrink the window of inconsistency. A node that was down longer than the window needs repair.

  4. Commit log, then memtable

    The replica writes the mutation to the commit log first. Then it puts the partition update in the current memtable. The trie path is the partition key. The rows for that partition sit in a B-tree. A later write to the same partition updates that B-tree.

  5. Ack, then flush later

    The replica acks. The client is done. Flush freezes the memtable, writes it as a sorted SSTable, and asks compaction to look at the new file.

Logged batches. A LOGGED batch is written to the batch log on other nodes first (syncWriteToBatchlog), then the mutations go out. If the coordinator dies after that log write, a peer replays the batch. An UNLOGGED batch skips the extra copy and only groups the network send.

4. Read Path

The data replica builds the merged partition. The other full replicas contacted for this read usually return a digest of that same result. Which replica gets the rows is the first full contact after the snitch sort. Tombstones are scanned on that replica even when the bytes sent back are small.

  1. Pick replicas and rank them

    ReplicaPlans.forRead takes the live natural replicas and sorts them with the snitch. The topology snitch puts the local address first when this node owns the token. DynamicEndpointSnitch keeps that order unless a score is worse than dynamic_snitch_badness_threshold (default 1.0, meaning more than twice as bad). The local node has no internode latency sample, so its score stays 0 unless severity is set. A slow first wave can add one more request. The table default, 99p, waits until the 99th percentile of recent latency.

  2. Ask one replica for rows, the others for a digest

    AbstractReadExecutor gives the actual rows to the first full replica in that order and a digest to the other contacted full replicas. Transient replicas get rows, not a digest. For quorum with three copies that is one data read and one digest. Consistency ONE contacts only the closest replica. Speculative retry set to ALWAYS starts with two data requests. The local read is sent after the remote messages, so a slow local disk does not delay the network.

  3. Find candidate files, then the partition inside each

    The data replica reads the memtable and View.select(LIVE, key), the interval tree of this table's live SSTables. Each equality candidate is checked with its bloom filter, then its primary index: the index summary on the BIG format, the on-disk trie on BTI. The default compaction strategy is size-tiered, so several overlapping files can all match. Leveled compaction is the special case where L0 overlaps and each higher level contributes at most one file.

  4. Merge cells

    All versions of the partition are merged. The cell with the newer timestamp wins. An equal timestamp keeps a tombstone over a live value. LIMIT counts live rows, so deleted rows are still walked until the limit is filled. That walk is why lots of tombstones make reads slow even when the result is small.

  5. Compare digests and return

    If the digests match, the coordinator returns the rows. If they do not, it fetches full data from the replicas and writes the newer cells back to the stale copies. That is read repair.

5. Compaction

Compaction rewrites SSTables the node already owns. A flush calls CompactionManager.submitBackground. The strategy decides which files. The table default is still size-tiered: buckets of similar size, compact when a bucket reaches the threshold. Unified compaction is the 5.0 strategy you set per table. It groups files by density, then by token overlap, and its pending-task number is that overlap divided by the threshold, plus work already running.

  1. A new file appears

    A flush, or a compaction that just finished, asks the table whether more compaction is needed.

  2. Pick the next group

    CompactionStrategyManager promotes or demotes repair files first. Size-tiered then picks a bucket of similar-sized files. Unified compaction, when selected, groups by density (size divided by token span) and compacts a bucket whose overlap exceeds the threshold. Its scaling parameter W chooses a leveled-like or a tiered-like fanout.

  3. Merge and replace

    The picked files are merged with the same cell and tombstone rules as a read. New SSTables are written, often split into shards. The old files drop out of the live set. If work ran, compaction looks for another group.

6. Lightweight Transactions

A normal write does not check what is already stored. An IF write does. That is a lightweight transaction, LWT, also called CAS. It is Paxos for a single partition. Cassandra will not coordinate a transaction across partitions.

CQL looks like UPDATE ... IF col = 1, INSERT ... IF NOT EXISTS, or DELETE ... IF EXISTS. The vote uses SERIAL or LOCAL_SERIAL. The commit uses a normal write consistency, chosen by the client, and cannot itself be SERIAL. The default paxos_variant is v1 (legacyCas). v2 is the same four phases with the read folded into prepare. StorageProxy.cas picks the variant.

  1. Prepare, and finish leftover work

    The coordinator asks a quorum to promise a ballot. In v1 the current partition is a separate quorum read after those promises. In v2 that read comes back with the prepare. An unfinished round is completed before a new one starts. A SERIAL SELECT uses this same read.

  2. Evaluate the condition

    The coordinator checks the IF against those current values. If it matches, the proposal is the client's update. If it does not, both variants still propose an empty update, so a later reader cannot resurrect a write this round rejected. The client result is [applied] false plus the row that blocked it.

  3. Propose, then commit on the write path

    A quorum must accept the proposal. The update is then committed as a normal mutation: commit log, then memtable, at the commit consistency. Success returns [applied] true. A higher ballot is contention, and the coordinator retries until the CAS timeout.

LWT is not a general transaction. It covers one partition. It costs several round trips. Use it for uniqueness and compare-and-set, not as the default write.

7. Storage-Attached Indexes

SAI is the Cassandra 5.0 secondary index. It lives next to the data, not in a hidden table. Each memtable and each SSTable has its own index for the indexed column. A query still goes to replicas that own the data. Those replicas use the index to find matching primary keys, then read those rows from the memtable and SSTables as usual. The component-by-component walkthrough is in Cassandra Storage-Attached Index.

Vector search is the same mechanism on a vector column: approximate nearest neighbor through SAI, then the matching rows.

  1. Index the write locally

    After SAI is created, each mutation also updates a memtable index for that column. Flush writes the SSTable and, beside it, the SAI files for the indexed columns. Compaction rebuilds those files for the output SSTables.

  2. Query, then read the matching rows

    The coordinator still sends the query to replicas that own the data. Each replica searches its memtable index and SSTable indexes, gets primary keys, and reads those rows with the ordinary merge. Tombstones and newer timestamps are applied there, not inside the index.

8. New Node Bootstrap

A new node starts from the seed list. Seeds are the first gossip contact. From a seed it learns the other members, their tokens, and each member's schema version. It downloads the schema, copies the ranges it will own, then tells the cluster it is NORMAL.

  1. Recover local disk

    The node loads system tables, replays the commit log, and reads schema from disk. A brand-new node has no user tables, so its schema version will not match the cluster.

  2. Ask the seeds before joining

    doShadowRound keeps sending an empty gossip syn to the configured seeds until one answers or the shadow round times out. The reply is that seed's endpoint map: peers, tokens, status, schema version. The map is stored aside from the live gossip state. It is used to reject an address collision and, by default, to refuse the join while any peer is already joining, leaving, or moving.

  3. Gossip, then download schema

    Regular gossip starts. With no live peers yet, each round contacts a seed. The seed's state includes the other members. When a member's schema version differs, this node requests the actual table definitions and writes them into its own schema tables. Any ring member with that version can answer. Streaming waits until that pull finishes.

  4. Copy data, then go NORMAL

    A non-seed with auto-bootstrap picks tokens and streams the ranges it will own. With a single token, system.local stores that token. The served range is from the predecessor through that token, computed from the current ring. After streaming succeeds, setTokens marks the node NORMAL and gossip publishes that status. Peers apply it on the next gossip exchange, in handleStateNormal. Join success is that local setTokens after streaming.

9. Incremental Repair

Replicas can drift: hints expire, a node was down too long, or a write never reached every copy. Incremental repair compares only the unrepaired data in a range, copies the differences, and later marks those files repaired so the next repair can skip them.

  1. Isolate the unrepaired range

    Each participant splits unrepaired SSTables that overlap the range. The in-range piece is tagged with this session. Already repaired files, and files from other sessions, stay out.

  2. Compare and copy differences

    Validation reads only those tagged files. Ranges that disagree are streamed. Matching ranges move no row data.

  3. Commit, then compact later

    Each node promises, flushes the repair table, then commits. The data files are still pending. A later compaction marks them repaired. A failed session demotes them the same way. Full repair skips this tagging and compares the unrepaired data in place.

10. Details Worth Keeping

These are the spots where the code is more specific than the one-line description.

Topic What this tree does
Write visibility The ack means commit log and memtable on enough replicas. The SSTable appears at flush.
Last write wins Resolution is per cell, by timestamp. Two writes to different columns of the same row both survive. Counters are summed.
Hints The coordinator stores a mutation for a down replica and replays it later. Hints expire. Repair still needed for long outages.
Who sends rows The first full contact after the snitch sort sends the merged rows. Other contacted full replicas send a digest. With the default scores, a coordinator that owns the token is that first contact.
Tombstone latency LIMIT counts live rows. Dead cells are still scanned. That count is TombstoneScannedHistogram.
LWT Default paxos_variant is v1. Prepare, read, propose, commit on one partition. A failed IF still proposes an empty update.
SAI Local index files next to each SSTable. The replica uses them to find keys, then reads those rows from its own data.
Compaction lag Default strategy is size-tiered. On unified compaction, pending tasks are overlap divided by the threshold, plus tasks already running.
Schema on a new node Gossip delivers a version UUID. The node then pulls the table definitions from a member with that version.
Join success The joining node marks itself NORMAL after streaming. Peers apply that state from gossip.
Single token The node persists its token. The served range is from the predecessor through that token, computed from the current ring.
Two nodes joining By default a node refuses to bootstrap while any peer is already joining, leaving, or moving.

Source Map

Class names below are from Cassandra 5.0. The links point at the cassandra-5.0 branch.

  • StorageProxy
    Coordinator for writes, digest reads, hinted handoff, and logged batches. cas hands LWTs to Paxos.
  • ColumnFamilyStore
    Replica apply into the memtable, and flush of that memtable to an SSTable.
  • SinglePartitionReadCommand
    Memtable plus covering SSTables, then the merged partition.
  • AbstractReadExecutor
    First replica gets the data request. Other contacted full replicas get a digest.
  • Paxos
    LWT: prepare and read, check the condition, propose, commit.
  • StorageAttachedIndex
    Local secondary index on memtables and SSTables, including vector search.
  • UnifiedCompactionStrategy
    Default strategy is size-tiered. Unified compaction adds density levels and the overlap estimate.
  • HintsService
    Writes a hint for a down replica and replays it after the node returns.
  • MigrationCoordinator
    Announces the local schema UUID and pulls a version this node has not received.
  • IncrementalRepairTask
    Registers the repair session. Isolation, validation, and finalize live in the consistent-session classes next to it.
