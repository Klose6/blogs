Designing a Distributed File System

Chunk storage Raft metadata Replication 15 min read

How do we store petabytes across ordinary machines while preserving a familiar file namespace, surviving disk loss, and streaming data at high throughput? The design separates strongly consistent metadata from a distributed chunk data plane.

01 / SCOPE

Optimize for large durable files

The system supports create, open, sequential and random reads, append, rename, list, snapshot, and delete. It targets large analytics, media, backup, and model files. Full POSIX semantics, memory-mapped I/O, and tiny-file workloads are explicitly outside the first version.

Functional

  • Hierarchical directories and file permissions
  • Streaming reads, append, rename, and delete
  • Snapshots and immutable file versions
  • Storage quotas and placement policies

Non-functional

  • Petabytes of logical data and billions of files
  • No acknowledged chunk lost after one node failure
  • High sequential throughput and horizontal scaling
  • Automatic repair, rebalancing, and corruption detection
Design boundary: this is a GFS-style file system, not an object store. It exposes directories and append, but relaxes expensive POSIX behavior such as arbitrary concurrent byte-range writes and cross-shard atomic transactions.
02 / CAPACITY

Size metadata separately from bytes

Assume 10 PB of logical data, one billion files, a 10 MB average file, 128 MB chunks, 100 GB/s aggregate reads, and 20 GB/s writes.

30 PB

triple-replicated data

Before moving colder files to erasure coding.

One billion files produce more metadata pressure than 78 million full chunks because most files are smaller than one chunk. Small files should be packed into immutable container files or redirected to an object store; otherwise namespace and disk-seek overhead dominate.

03 / LAYOUT

Split files into immutable-versioned chunks

File inode
  file_id:      0199f...
  version:      17
  size:         402,653,184 bytes
  chunks: [
    { index: 0, chunk_id: c_842, version: 3 },
    { index: 1, chunk_id: c_843, version: 1 },
    { index: 2, chunk_id: c_844, version: 1 }
  ]

A 128 MB chunk amortizes metadata and supports large sequential I/O. Each chunk has a stable ID, generation number, checksum table, and replica locations. Clients translate a byte offset into a chunk index, then transfer bytes directly to storage nodes.

04 / HIGH LEVEL

Keep file bytes off metadata servers

Clients consult metadata for chunk locations and leases, then bypass that plane for high-bandwidth transfers to storage nodes.

05 / CONTROL PLANE

Replicate and shard namespace metadata

Metadata contains inodes, directory entries, permissions, file-to- chunk mappings, chunk generations, leases, snapshots, and placement intent. Each metadata tablet is a three- or five-node Raft group, so namespace changes commit only after a quorum persists the log.

A small root directory maps inode ranges or directory subtrees to tablets. Split hot tablets by inode range; avoid permanently tying a shard to one top-level directory because one tenant may become hot. Clients cache routing and chunk-location metadata with versions and short leases.

Strongly consistent

Create, rename within a shard, delete, permission changes, chunk generation, and primary lease ownership.

Eventually consistent

Replica inventory, disk utilization, access heat, repair progress, and cached chunk locations.

Cross-shard rename needs a transaction coordinator or a restricted semantic. The first version supports atomic rename only within one namespace shard and implements cross-shard move as copy plus delete.

06 / READ PATH

Resolve once, stream directly

  1. Resolve the path. The client asks the namespace router for an inode, file version, chunk ID, and generation.
  2. Select a replica. Metadata returns healthy locations ordered by rack, region, load, and network proximity.
  3. Read bytes directly. The client sends chunk ID, generation, byte range, and authorization token to a chunk node.
  4. Verify checksums. The client validates each data block and retries another replica on mismatch or timeout.
  5. Report corruption. A background signal asks the repair service to quarantine and reconstruct the bad replica.

Cache file-to-chunk metadata until its lease or version expires. Stream sequential reads from multiple chunk replicas in parallel, but limit read-ahead so one abandoned request does not waste network.

07 / WRITE PATH

Order writes through a leased primary

  1. Allocate. Metadata selects three chunk nodes in distinct failure domains and grants one a fenced primary lease.
  2. Pipeline data. The client streams bytes to the closest replica, which forwards them to the next. Every replica buffers the same data under a write ID.
  3. Choose order. The client asks the primary to commit. The primary assigns a serial mutation sequence.
  4. Apply everywhere. Replicas verify the lease epoch, write data and checksums, fsync according to policy, and acknowledge.
  5. Commit metadata. After the required acknowledgements, the file length and chunk generation advance atomically. 
write identity:
  (file_id, chunk_index, file_version, client_request_id)

fencing:
  accept only if lease_epoch == current_chunk_epoch

success:
  primary + at least one cross-zone replica persisted

Stable client request IDs make retries idempotent. A stale primary cannot commit after failover because every replica rejects its old lease epoch. Concurrent appends are ordered by the current primary; arbitrary overlapping writes are rejected or serialized.

08 / STORAGE

Replicate hot data, erasure-code cold data

PolicyStorage overheadBest use
3× replication200% extraHot writes, fast reads, and simple repair
6+3 erasure coding50% extraCold immutable files with lower storage cost
Single copyNo extraOnly disposable scratch data

New and frequently accessed chunks use three replicas. A background lifecycle job converts sealed cold files into six data and three parity fragments across failure domains. Any six fragments reconstruct the chunk. Reads usually fetch only data fragments; repair uses parity.

Checksums and scrubbing

Store a CRC32C checksum for every 64 KB data block and a cryptographic hash for whole immutable chunks. Verify checksums on read and during periodic scrubbing. Silent corruption is a normal storage failure, not an exceptional impossibility.

09 / RECOVERY

Rebuild from desired state and inventory

Chunk nodes send heartbeats with disk health, capacity, and a digest of chunk inventory. Full inventory scans reconcile actual chunks against metadata after restart. Metadata records desired placement; chunk nodes report physical reality.

  • Disk failure: quarantine the device and copy affected chunks from healthy replicas.
  • Node failure: expire its heartbeat and prioritize chunks below minimum durability.
  • Rack loss: placement rules ensure another rack already owns a copy or parity fragment.
  • Metadata leader failure: Raft elects a follower with the committed log.
  • Stale replica: reject old generations and garbage-collect only after a safety delay.
  • Corrupt replica: quarantine, read from another copy, and reconstruct in the background.

Rate-limit repair so it does not consume all foreground bandwidth. Prioritize chunks with zero or one healthy copy, then restore placement diversity, then rebalance capacity. Repair reads should come from multiple source nodes to avoid creating a recovery hot spot.

Rebalancing

The placement service considers free space, disk and network load, rack diversity, and access heat. Copy a chunk to its target and verify checksums before deleting the old replica. Never move the final healthy copy, and add hysteresis so chunks do not oscillate between nodes.

10 / SEMANTICS

State the consistency model precisely

Namespace

Linearizable within a metadata shard. A successful create, permission change, or same-shard rename is immediately visible.

File contents

Immutable file versions are strongly readable. Appends become visible after the primary commits the new length and generation.

Readers pin a file version when opening it, giving a stable snapshot while new appends continue. A fresh open sees the latest committed version. Snapshots copy metadata references, not bytes; copy-on-write creates new chunks only when data changes.

Deletion is two phase: first tombstone the namespace entry so new opens fail, then garbage-collect unreferenced chunks after snapshots, leases, and a recovery grace period expire.
11 / MULTI-REGION

Keep synchronous writes within one region

A volume has a home region whose metadata Raft groups and synchronous chunk replicas span availability zones. Cross-ocean quorum writes would add unacceptable latency and lose availability during a wide-area partition.

Replicate sealed file versions and the namespace journal asynchronously to a disaster-recovery region. Read-only replicas may serve immutable versions there. Promote the backup only after fencing the old region and choosing a journal recovery point; recent acknowledged writes need cross-region synchronous replication only for explicitly premium volumes.

Regional reads

Cache or replicate immutable hot chunks near readers. Metadata tokens pin the exact version and prevent mixed-version files.

Active-active writes

Avoid them for one namespace. Assign different volumes or subtrees to different home regions instead of merging conflicts.

Building a file system is rarely the right business choice. Use CephFS when you need a mature POSIX-like distributed file system, HDFS for Hadoop-oriented large-file analytics, or S3 when object semantics are sufficient. Build this design only for requirements those systems cannot satisfy.

Production signals

  • Metadata operation latency, Raft commit time, and tablet hot spots
  • Read/write throughput and tail latency by chunk node and disk
  • Under-replicated, unavailable, corrupt, and stale chunks
  • Repair queue age, reconstruction bandwidth, and time to durability
  • Disk fullness, placement diversity, and rebalancing movement
  • Checksum failures, lease fencing rejects, and client retry rate

Final design summary

Raft-replicated metadata shards own the namespace, chunk maps, and fenced write leases. Clients resolve metadata once, then stream bytes directly to chunk nodes. Hot chunks use cross-zone replication; cold immutable files use erasure coding. Checksums detect silent corruption, heartbeats and inventory rebuild desired placement, and controlled repair restores durability. Home-region writes keep latency practical, while immutable versions and asynchronous replication support remote reads and disaster recovery.
