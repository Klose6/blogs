Designing a Distributed Task Scheduler

Time buckets Leases At-least-once 15 min read

How do we run millions of one-time and recurring tasks close to their deadlines without losing work or executing it uncontrollably twice? The design separates durable scheduling from dispatch and execution.

On this page Requirements Capacity Delivery semantics Architecture Data model Scheduling loop Worker execution Recurring tasks Retries and recovery Multi-region Technology stack
01 / SCOPE

Schedule durably, execute independently

Clients create one-time or cron schedules, cancel pending tasks, inspect status, and configure retries. Workers execute registered task types. This design is a scheduler, not a general workflow engine: dependency graphs, human approvals, and long-lived sagas should use a system such as Temporal.

Functional

  • One-time, delayed, and recurring schedules
  • Task cancellation and status inspection
  • Priorities, retry policy, timeout, and dead letter
  • Tenant quotas and task-type routing

Non-functional

  • No acknowledged schedule is silently lost
  • 99% dispatch within one second of due time
  • At-least-once execution with bounded duplicates
  • Horizontal scaling to billions of active schedules
Critical distinction: dispatching on time and finishing on time are different SLOs. The scheduler controls when work becomes available; worker capacity and downstream latency control completion.
02 / CAPACITY

Estimate active timers and due-task bursts

Assume one billion active schedules, 100 million executions per day, a 10× burst at minute and hour boundaries, and a 2 KB task record including indexes and retry metadata.

Average throughput is modest compared with event systems, but time distribution is adversarial. Customers naturally choose midnight, the top of an hour, or a round minute. Add jitter where semantics allow it and provision for synchronized bursts.

03 / CONTRACT

Promise at least once, require idempotency

GuaranteeRealityDecision
At most once A crash after marking complete but before execution can lose work Wrong default for important tasks
At least once Lease expiry and acknowledgement loss can cause a retry Chosen: no loss, but handlers must deduplicate
Exactly once Cannot cover arbitrary external side effects atomically Achieve only per effect with idempotency or transactions

Every execution carries a stable execution_id. A payment handler passes it as the provider's idempotency key; a database handler stores it in a unique column in the same transaction as its business change. The scheduler never claims that a worker process ran exactly once.

04 / HIGH LEVEL

Separate storage, timing, and execution

Coordinators own time shards and create durable outbox records; Kafka separates dispatch from worker capacity and retry recovery.

05 / DATA MODEL

Partition schedules by time and shard

Task {
  task_id:          string
  tenant_id:        string
  task_type:        string
  payload_ref:      string
  scheduled_at:     timestamp
  bucket:           "2026-09-15T22:30#037"
  status:           SCHEDULED | READY | RUNNING |
                    SUCCEEDED | RETRY_WAIT | FAILED | CANCELLED
  attempt:          integer
  execution_id:     string
  lease_until:      timestamp?
  schedule_version: integer
}

The DynamoDB partition key combines a one-minute UTC bucket with a virtual shard, and the sort key is scheduled_at#task_id. A coordinator queries only its owned shards for the current horizon. Randomly assigning one of hundreds of virtual shards prevents every midnight task from creating one hot partition.

A task-ID index supports status and cancellation lookups. Large payloads live in S3; the task stores an immutable object reference and checksum. DynamoDB transactions update task state and create an outbox item atomically.

Do not scan all tasks for “due now.” Time buckets turn a global search into bounded range reads. Virtual shards spread each bucket across storage partitions and coordinator instances.
06 / TIMING

Use durable buckets plus an in-memory wheel

  1. Acquire virtual shards. Coordinators hold fenced etcd leases and stop dispatching immediately if renewal fails.
  2. Prefetch a short horizon. Query the next five minutes of owned DynamoDB buckets and load tasks into a hierarchical timing wheel.
  3. Advance the wheel. A monotonic clock wakes slots at 100 ms resolution; wall-clock UTC determines whether a task is due.
  4. Claim conditionally. Transition SCHEDULED → READY only if the schedule version and state still match.
  5. Create an outbox record. Commit it in the same DynamoDB transaction, then let the relay publish to Kafka.

The wheel is an optimization, not the source of truth. After restart, a coordinator rebuilds it from DynamoDB. Query overlapping buckets and keep a recovery scan behind the current time so a pause or lease transfer cannot skip overdue tasks.

Why not one Redis sorted set?

A sorted set works at modest scale, but billions of timers create a memory-heavy central structure, expensive failover, and hot range queries around common deadlines. Durable time buckets provide explicit partitioning; each coordinator keeps only its near-term working set in memory.

07 / WORKERS

Lease work before performing side effects

  1. A worker group consumes the Kafka topic for its task type and priority.
  2. The worker conditionally transitions READY → RUNNING, sets a unique execution token, and records a lease deadline.
  3. Long tasks heartbeat before the lease expires. The payload includes the stable execution ID for downstream idempotency.
  4. Success conditionally writes SUCCEEDED using the same execution token, then acknowledges Kafka.
  5. A stale worker whose lease was replaced cannot update status because its execution token no longer matches.

Do not hold a Kafka message unacknowledged for a six-hour task. The durable task lease records ownership; the consumer can commit after the claim. A lease reaper later detects abandoned RUNNING tasks and creates a new attempt.

08 / RECURRENCE

Materialize recurring occurrences safely

Store the cron expression, IANA time zone, next occurrence, and a misfire policy in a schedule record. Materialize only a small number of future task occurrences. Each occurrence ID is deterministic: schedule_id + scheduled_utc_time.

Misfire policyBehavior after downtimeUse case
SkipIgnore missed runs and schedule the next future timePeriodic cache refresh
Fire once nowCollapse all missed runs into one executionSummary or synchronization
Catch up allCreate each missed occurrence with rate limitsFinancial processing

Daylight-saving transitions make local times ambiguous or nonexistent. Use an IANA zone database and define whether “02:30 every day” skips, moves, or executes twice during a transition. Store every concrete occurrence in UTC after applying that policy.

A recurrence materializer uses a conditional next_occurrence update and deterministic occurrence IDs, so concurrent retries cannot create duplicates.

09 / RECOVERY

Make every transition replayable

FailureRecovery
Coordinator dies before claimNew lease owner reloads overlapping due buckets
Claim commits, relay diesDurable outbox remains and another relay publishes it
Kafka publishes twiceWorker's conditional READY claim accepts only one execution
Worker dies during executionLease expires; reaper creates a new attempt with the same effect ID
Completion response is lostRetry observes SUCCEEDED or downstream idempotency record

Retry policy

Use exponential backoff with full jitter and a maximum attempt count. Distinguish transient errors from permanent validation errors. Rate limits and explicit retry-after values override generic backoff. Store the next attempt as another scheduled task rather than sleeping a worker thread. 

delay = random(0, min(max_delay, base × 2^attempt))

Exhausted or permanent failures move to a dead-letter store with the payload reference, error class, attempts, and code version. Operators can inspect and redrive after correcting the cause. Redrive preserves the original task and execution identities.

10 / MULTI-REGION

Give each schedule one home region

Assign schedules to a home region by tenant or explicit data-residency policy. That region owns timing and state transitions; workers may run elsewhere when the task type permits. This avoids two regions dispatching the same due task during replication lag.

Replicate schedule records and outbox state to a failover region. On outage, obtain a global fencing epoch, wait for or verify the replicated watermark, then allow the failover coordinator to acquire shard leases. Some duplicates remain possible, so execution idempotency is still required.

Short regional outage

Preserve single ownership and dispatch overdue tasks when the home returns. This favors duplicate control over punctuality.

Extended outage

Promote the replica with a fenced epoch and apply each task's misfire policy. This favors availability with bounded duplicates.

Production signals

  • Due-to-dispatch and due-to-start latency by tenant and task type
  • Time-bucket query latency, shard skew, and prefetch horizon coverage
  • Coordinator lease renewal and ownership changes
  • Outbox age, Kafka lag, and worker queue depth
  • Running lease expirations, retry rate, and duplicate claims
  • Success, permanent failure, timeout, and dead-letter rate

Final design summary

DynamoDB stores schedules in sharded time buckets, while etcd gives each coordinator fenced ownership of virtual shards. Coordinators prefetch a short horizon into timing wheels and atomically create outbox records for due work. Kafka decouples dispatch from Kubernetes worker pools. Execution leases recover abandoned tasks, deterministic IDs make side effects idempotent, and explicit misfire policies make recurring schedules predictable through downtime and clock changes.
