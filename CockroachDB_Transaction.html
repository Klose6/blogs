CockroachDB Distributed Transactions

How a serializable transfer updates two key ranges atomically using MVCC, Hybrid Logical Clocks, Raft, write intents, write pipelining, and Parallel Commits—without requiring specialized atomic-clock hardware.

1. The Mental Model

CockroachDB separates two responsibilities. Raft makes each range's changes durable and replicated; the transaction protocol makes changes spanning several independently replicated ranges appear atomic. MVCC timestamps order versions, while intents and a transaction record connect provisional writes into one transaction.

The central idea: data is first written as provisional MVCC values called write intents. A single transaction record determines whether all those intents are logically visible or must be discarded. Parallel Commits lets the final transaction record and outstanding intent writes reach Raft consensus at the same time.

Isolation

This article follows CockroachDB's Serializable execution. Conflicting operations wait, push timestamps, refresh earlier reads, or retry so the result is equivalent to a serial ordering.

Durability

Every intent and transaction-record update is proposed by a range leaseholder and replicated to that range's Raft quorum before it is considered durable.

Time

An HLC timestamp combines physical time with a logical counter. It preserves causality and remains close to wall time, while configured clock-offset bounds detect unhealthy clocks.

Atomicity

Readers treat intents according to the referenced transaction's status. This indirection makes all writes commit or abort together even though they live on different ranges.

2. Example: Transfer $100 Across Two Ranges

Assume Alice's row maps to Range 1, Bob's row maps to Range 2, and both ranges have separate leaseholders and Raft groups.

BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;  -- Alice: key K1 on Range 1

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;  -- Bob: key K2 on Range 2

COMMIT;

The safety invariant is that Alice's debit and Bob's credit become visible together. A crash must never leave only one side committed. The examples below use a transaction record anchored on Range 1, near the first write.

The record is not necessarily written when BEGIN runs. CockroachDB normally creates transaction records lazily. An intent can contain enough transaction metadata to point to an anchor key even while no record exists there yet.

3. Components on the Write Path

Component Responsibility in this transfer
SQL gateway / transaction coordinator The gateway receiving the session runs the KV transaction through TxnCoordSender. It tracks timestamps, read/write spans, outstanding writes, retries, heartbeats when needed, and finalization.
DistSender Looks up range descriptors, splits KV batches at range boundaries, and routes each sub-batch to the proper leaseholder.
Range leaseholder Sequences requests for one range, applies concurrency control, and proposes mutations to that range's Raft group.
Raft replicas Replicate each range-local intent or transaction-record update to a quorum for durability and availability.
MVCC intent + lock table The durable intent stores the provisional value and transaction metadata. The in-memory lock table queues conflicting requests; it is not a global lock manager.
Transaction record A single, replicated record at the transaction's anchor tracks PENDING, STAGING, COMMITTED, or ABORTED.

Architecture Graph

The request path is a graph: one coordinator fans writes out to independent ranges, and each range fans replication out to its own Raft quorum.

4. Step-by-Step Transaction Lifecycle

  1. Start and assign an HLC timestamp

    The gateway creates in-memory transaction state with a unique transaction ID, an anchor key, an epoch, priority, and read/write timestamps. Reads use MVCC versions at the transaction's read timestamp. A durable transaction record is usually not created yet.

  2. Read both balances

    The coordinator routes reads to the leaseholders for Range 1 and Range 2. It remembers the read spans so those reads can later be refreshed if a conflict pushes the commit timestamp forward.

  3. Write provisional values

    Each update becomes a replicated MVCC intent rather than a committed value. Conceptually:

    K1 @ T → { value: 900, txn: [id, anchor=K1, epoch, sequence, T] }
K2 @ T → { value: 600, txn: [id, anchor=K1, epoch, sequence, T] }

    Each leaseholder checks conflicts and proposes its intent through its own Raft group. The intents carry sequence numbers so retries are idempotent and recovery can verify exactly which writes exist.

  4. Pipeline independent writes

    The txnPipeliner may return from a transactional write before its Raft proposal has finished, marking it as an in-flight write. A later dependent operation first issues a QueryIntent proof. This overlaps replication with useful work but does not weaken durability: commit still needs proof for every outstanding write.

  5. Commit with a conditional STAGING record

    When eligible for Parallel Commits, the final batch sends remaining writes to their ranges while sending EndTxn to the transaction-record range. EndTxn writes a STAGING record containing the unresolved in-flight writes and their expected sequence numbers.

    Writes already proven are represented as lock spans for later cleanup; the in-flight list is not necessarily a list of every key the transaction touched.

  6. Acknowledge the implicit commit

    The coordinator returns success only after both conditions hold:

    1. The STAGING transaction record is durably replicated.
    2. Every in-flight write named by that record is acknowledged at the expected timestamp and sequence.
    Commit rule: STAGING + all promised writes exist ⇒ implicitly COMMITTED. A STAGING record by itself is not sufficient.

  7. Finalize and resolve intents asynchronously

    After success can be returned, CockroachDB changes the transaction record to explicit COMMITTED and resolves intents into ordinary committed MVCC values. This cleanup is asynchronous. A request that encounters an unresolved intent can inspect or recover the transaction and help resolve the intent.

Why Parallel Commits Saves Latency

Classic sequential commit:
  finish every intent write ──Raft──▶ write COMMITTED record ──Raft──▶ reply

Parallel Commit:
  remaining intent writes ──Raft──┐
                                   ├── all succeeded ──▶ reply
  write STAGING record ─────Raft──┘
                                      └─ async: COMMITTED + resolve intents

This optimization removes an extra sequential consensus round from the commit path. It does not make every transaction a single-round operation: earlier SQL statements, reads, conflicts, and non-pipelined writes may already have incurred RPC and Raft rounds.

5. Crashes and Transaction Recovery

Because a coordinator can disappear at any point, another node must be able to determine the outcome from replicated state alone. A recovery request checks the transaction record and, when necessary, the in-flight write proofs.

Observed state Recovery decision Visible result
No record, or abandoned PENDING A competing request may push/abort the transaction after liveness and priority checks. Any intents are removed; neither transfer update commits.
STAGING and every listed in-flight write exists Recover as COMMITTED. Both debit and credit become visible.
STAGING but any listed write is missing or mismatched Recover as ABORTED. Neither provisional value becomes visible.
Explicit COMMITTED or ABORTED Resolve leftover intents according to that final state. Committed intents become values; aborted intents are removed.
Client timed out after sending COMMIT Outcome may be ambiguous to the client even though the cluster can recover it. Use an idempotency key or query application state before retrying an external action.

6. Concurrency Control and Conflicts

CockroachDB is not accurately described as a purely optimistic system. It combines MVCC with durable intents, in-memory lock-table queues, timestamp pushes, deadlock detection, read refreshes, and transaction retries.

Reader meets an intent

A reader can ignore a future intent when reading an older MVCC snapshot. If an unresolved intent conflicts with the read, the request enters the lock wait queue and may push the intent's transaction to learn whether it should wait, abort it, or resolve a finished intent.

Writer meets an intent

A conflicting writer normally waits. Push logic considers liveness, priorities, and transaction state; one transaction can be aborted to break a conflict, and distributed deadlock detection handles cycles of waiters.

Write meets a later read

The timestamp cache records recent reads. A writer arriving at an older timestamp must move its write timestamp above a conflicting read, then prove that its own earlier reads remain valid.

Write meets a newer value

A write-too-old conflict pushes the transaction timestamp forward. The transaction can continue only if read refresh succeeds; otherwise CockroachDB retries it at a newer timestamp.

7. HLC, Uncertainty, and Read Refresh

These mechanisms are related, but they solve different problems:

  • Hybrid Logical Clock: an ordered pair of wall time and a logical counter. Nodes update their HLCs when sending and receiving messages, preserving causality while retaining a useful relationship to physical time.
  • Clock uncertainty: because clocks are synchronized rather than atomic, a node may encounter a version whose timestamp is slightly in its apparent future. Observed timestamps narrow what is uncertain on nodes already contacted; otherwise the transaction may need a higher timestamp or retry. The bound is a cluster setting, not a universal fixed 250 ms.
  • Read refresh: after a conflict pushes the transaction's write/commit timestamp from T1 to T2, CockroachDB checks whether any previously read span changed in (T1, T2]. If not, it can commit at T2; if data changed, it retries.
read at T1 ──▶ conflict pushes commit timestamp to T2
                    │
                    ▼
        scan prior read spans for changes in (T1, T2]
                    │
             ┌──────┴──────┐
         unchanged       changed
             │              │
       commit at T2     retry transaction

8. Fast Paths and Latency Boundaries

Path When it applies What it saves
One-phase commit (1PC) The complete transaction, including commit, fits in one eligible batch on one range. The range can apply the writes as committed in one consensus operation without a distributed transaction record and unresolved intents.
Same-range STAGING bypass The record and all in-flight writes are evaluated on the same range, so their success is known atomically. The range can avoid leaving a conditional STAGING state.
Cross-range Parallel Commit The transaction meets protocol eligibility requirements and writes several ranges, as in this transfer. Overlaps outstanding writes with the staging-record proposal, removing a sequential consensus round from commit.
Non-parallel commit The transaction uses features or request shapes that are not eligible for Parallel Commits. No special saving: CockroachDB first proves writes, then finalizes the transaction record.

10. Corrections to Common Simplifications

Simplified claim More accurate model
“A PENDING record is created at transaction start.” Records are normally lazy. Intents can refer to an anchor before a record exists; commit, heartbeat, or a push can create it when needed.
“STAGING means committed.” It means conditionally committed. Every promised in-flight write must exist at the expected sequence and timestamp; a missing write causes recovery to abort.
“The staged record lists every written key.” Its in-flight list contains writes still requiring proof. Already proven writes are tracked as lock spans for cleanup.
“Parallel Commits makes the whole transaction one round.” It removes an additional sequential consensus round from the commit path. Earlier statements and conflicts can still require more rounds.
“Reader cleanup is intent pipelining.” Write pipelining overlaps replication. Cleanup is intent resolution; coordinators and later requests can perform it.
“CockroachDB concurrency control is purely optimistic.” It combines MVCC and retries with intents, lock-table waiting, transaction pushes, and deadlock handling.
“Clock uncertainty and read refresh are the same.” Uncertainty handles possible future versions caused by clock skew. Refresh proves old reads are still valid after a timestamp push.
