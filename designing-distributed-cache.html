Designing a Distributed Cache

Consistent hashing Eviction Replication 14 min read

How do we serve millions of low-latency lookups while nodes fail, capacity changes, and hot keys appear without warning? The design partitions an in-memory working set, replicates it across zones, and treats every cached value as safely disposable.

01 / SCOPE

A cache accelerates truth; it is not truth

The service stores opaque key-value entries in memory and supports get, multi-get, set, compare-and-set, delete, and expiration. It reduces load on databases and external services. Losing every cache entry must hurt performance, not correctness.

Functional

  • Get, set, delete, multi-get, and TTL
  • Atomic add and compare-and-set
  • Automatic sharding and replica failover
  • Namespace quotas and invalidation events

Non-functional

  • Reads below 2 ms at p99 within a region
  • At least one million operations per second
  • No single shard or availability-zone dependency
  • Bounded stale data under a documented policy
Core contract: callers must tolerate misses, evictions, and brief unavailability by loading authoritative data. If losing an entry breaks correctness, that entry belongs in a database or durable coordination system—not only in this cache.
02 / CAPACITY

Size memory, throughput, and network

Assume a 10 TB logical working set, 5 KB average value, one million peak operations per second, a 90% read ratio, and two in-memory copies of each entry.

2B

cached keys

20+ TB

physical memory

Two copies plus allocator and key overhead.

40 Gbps

value traffic

One million operations/s at roughly 5 KB.

Keep individual Redis processes near 25–50 GB so failover, restart, and rebalancing remain manageable. The workload therefore requires hundreds of shards, distributed across racks and availability zones, with headroom for skew and a node failure.

03 / INTEGRATION

Choose a pattern per data type

PatternHow it worksBest use
Cache-aside Application reads cache, loads the database on miss, then fills cache General read-heavy data; simplest default
Read-through Cache service invokes a registered loader on miss Shared loading policy, at the cost of tighter coupling
Write-through Write reaches cache and database synchronously Read-after-write needs, but increases write latency
Write-behind Cache acknowledges first and persists later High write throughput only when data loss is acceptable

Use cache-aside for the shared platform. Keep database ownership in application services and use Kafka change events for invalidation. Reserve write-behind for disposable aggregates; it violates the rule that the cache is not the source of truth.

04 / HIGH LEVEL

Separate routing, data, and control planes

The client library routes keys to primary shards; replicas serve failover, while database changes return through an invalidation branch.

Direct client-to-shard routing removes a proxy bottleneck and one network hop. Redis Cluster publishes its hash-slot map; clients cache it and follow MOVED or ASK redirects during rebalancing. A proxy remains useful for untrusted or simple clients, but must scale as a separate stateless tier.

05 / SHARDING

Map keys with stable ownership

Simple modulo hashing—hash(key) % node_count—moves most keys whenever the node count changes. Consistent hashing limits movement to the ranges owned by an added or removed node.

MethodBenefitTrade-off
Hash ringMinimal movement with virtual nodesRing management and uneven ranges
Rendezvous hashingSimple top-N replica selectionScores every candidate node without optimization
Redis hash slotsFixed 16,384 slots make migration explicitCluster-specific redirects and operations

Use Redis Cluster's 16,384 hash slots for the concrete implementation. Assign many slots to each primary and move slots incrementally during scaling. Hash tags such as {user:842}:profile place related keys together when a multi-key operation requires it, but overusing one tag creates a hot shard.

Hot keys

Hashing distributes keys, not requests. One viral key can still saturate its owner. Add a small in-process cache with a one-to-five second TTL, replicate read-only hot values under salted keys, or have replicas serve stale-tolerant reads. Detect hot keys from per-key samples rather than waiting for whole-shard CPU alarms.

06 / AVAILABILITY

Replicate across failure domains

Give every primary at least one asynchronous replica in a different availability zone. Redis Cluster nodes exchange health through a gossip bus; a majority of primaries must agree that a primary failed before promoting its replica.

Asynchronous replication

Keeps writes fast, but the newest cache entries may disappear during failover. Callers reload them from the source of truth.

Synchronous replication

Reduces lost cache writes but adds latency and still does not turn the cache into a durable database.

Choose asynchronous replication because availability and latency matter more than preserving disposable cache entries. Do not enable persistence merely to claim durability; use AOF only when faster warm-up justifies its write and recovery cost.

07 / MEMORY

Combine TTL with TinyLFU-style admission

TTL limits staleness; eviction creates room under memory pressure. They solve different problems. Add small random jitter to expiration so a large batch does not expire simultaneously.

PolicyBehaviorWeakness
LRUEvicts the least recently used entryA scan can evict the useful working set
LFURetains frequently used entriesOld popularity can linger without decay
FIFOEvicts the oldest inserted entryIgnores actual reuse
TinyLFUAdmits new entries only when likely more usefulRequires approximate frequency tracking

Redis provides approximate LFU through allkeys-lfu, a practical default for mixed shared workloads. Set per-namespace TTL ceilings and value-size limits. Rejecting a 50 MB value is usually better than letting it evict thousands of frequently reused objects.

08 / MISS CONTROL

Prevent one miss from becoming thousands

When a popular key expires, many callers may miss together and overwhelm the database. This cache stampede is often more dangerous than low hit rate.

Request coalescing

Use Go's singleflight inside each service so one goroutine loads a key while local waiters share its result.

Distributed lease

One caller acquires a short Redis SET NX PX lease. Others wait briefly, serve stale data, or retry with jitter.

Stale-while-revalidate

Keep a stale copy beyond soft expiry. One background loader refreshes it while latency-sensitive callers use the old value.

Probabilistic early refresh

As expiry approaches, increasingly allow a request to refresh. Work spreads over time instead of clustering at one instant.

Never hold a loader lease indefinitely. Give it a short TTL, attach a fencing token when writes matter, and make the cache fill conditional on the source version so a slow loader cannot overwrite newer data.
09 / INVALIDATION

Close the stale-fill race

The dangerous cache-aside race is not only a lost invalidation: a reader can fetch old database value V1, a writer commits V2 and deletes the cache, then the slow reader fills V1 after the deletion. 

reader: DB read V1 ─────────────── cache SET V1
writer:        DB write V2 → cache DELETE

result: cache contains stale V1

Include the database row version in every cache value and update a lightweight version watermark during CDC invalidation. A fill uses compare-and-set and succeeds only if its version is not older than the watermark. Simpler systems can use delete-after-write plus a short TTL, accepting bounded staleness.

Change-data capture

Debezium reads committed PostgreSQL changes and publishes versioned invalidations to Kafka. Regional consumers delete or update Redis entries idempotently. Partition events by entity key so each cache sees updates in database commit order.

For read-your-writes, the writer can update its local cache, bypass cache until a version is observed, or return the new object directly to the client. Do not require global cache coherence for every read.

10 / OPERATIONS

Fail as misses, then protect the database

  • Primary failure: promote the cross-zone replica and refresh client slot maps.
  • Network timeout: use a 1–2 ms regional timeout; fall back instead of queueing requests.
  • Shard addition: migrate small slot batches and rate-limit transfer bandwidth.
  • Cold restart: warm only critical keys and let normal traffic repopulate the rest gradually.
  • Bad client: enforce namespace memory, QPS, connection, and value-size quotas.
  • Cache outage: activate database admission control, request coalescing, and graceful feature degradation.

“Fall back to the database” is unsafe if all cache traffic moves there at once. Give loaders a bounded semaphore, apply circuit breakers, and reject optional work. The cache and source must have a coordinated overload plan.

Rebalancing

Move one slot range at a time from a source primary to a target. During migration, clients follow Redis ASK redirects. Track migration bandwidth, hit rate, and source latency; pause when user-facing p99 degrades. Add capacity before utilization is critical.

11 / MULTI-REGION

Keep cache state regional

Run an independent Redis Cluster in every region. Applications use only the local cluster; synchronous cross-region cache access would erase the latency benefit and reduce availability.

Source databases replicate according to their own consistency contract. Kafka carries invalidations to each region. A remote cache may briefly contain a value newer than its local database replica, so invalidation consumers should delete by version rather than push data that the local source cannot yet confirm.

Regional failover

Treat the destination cache as cold. Ramp traffic gradually and coalesce misses to protect the destination database replica.

Global configuration

Distribute namespace quotas and TTL policies through a versioned control plane; cache data itself remains local and disposable.

Use Memcached when values are simple, replication is unnecessary, and operational simplicity matters more than Redis data structures. Use Redis Cluster for this design because atomic compare-and-set, replicas, explicit slot migration, and rich expiration controls are requirements—not because every cache automatically needs Redis.

Production signals

  • Hit rate and byte hit rate by namespace
  • Get/set p50, p95, and p99 latency by shard
  • Memory fragmentation, eviction rate, and expired keys
  • Hot keys, network bandwidth, CPU, and connection saturation
  • Replica lag, failover duration, and slot migration progress
  • Loader concurrency, database fallback rate, and CDC lag

Final design summary

Redis Cluster partitions keys into movable hash slots and replicates each primary across zones. Cluster-aware Go clients route directly to owners, while local Ristretto caches absorb the hottest keys. LFU eviction and jittered TTLs manage memory; singleflight, leases, and stale-while-revalidate prevent stampedes. Debezium and Kafka distribute versioned invalidations, and independent regional clusters keep the hot path fast. Most importantly, every failure degrades to a controlled cache miss—not incorrect application state.
