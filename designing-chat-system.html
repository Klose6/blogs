Designing a Chat System

WebSockets Message ordering Fan-out 14 min read

How do we deliver messages in real time across millions of persistent connections, preserve conversation order, and synchronize every device? The design combines connection gateways, a durable ordered log, and replayable per-user state.

01 / SCOPE

Define delivery, not just sending

The system supports one-to-one and group conversations, text and attachments, online delivery, offline synchronization, delivery receipts, read state, typing indicators, and presence. Voice, video calls, public channels, and end-to-end encryption are related but separate designs.

Functional

  • Send, receive, edit, and delete messages
  • Synchronize history across multiple devices
  • Support groups and membership changes
  • Expose delivered, read, typing, and presence state

Non-functional

  • Online delivery below 200 ms at p99
  • No acknowledged message is silently lost
  • Stable order inside each conversation
  • Millions of concurrent connections
Delivery semantics: the backend provides at-least-once delivery. Clients make it look exactly once by assigning stable message IDs and deduplicating retries. “Delivered” means a recipient device acknowledged the message—not merely that a server accepted it.
02 / CAPACITY

At 50,000 sockets per gateway, 10 million connections require about 200 gateway instances before headroom. Socket count, heartbeat load, and network egress determine gateway capacity; message rate and partition skew determine Kafka and storage capacity.

03 / CONNECTIONS

Use WebSockets with resumable sessions

Clients establish a TLS WebSocket after obtaining a short-lived access token over HTTPS. WebSockets support low-overhead bidirectional messages, receipts, presence, and server push. Mobile clients may disconnect frequently, so correctness cannot depend on a permanent socket.

Heartbeats detect dead connections and refresh a short-lived session record. Apply backpressure per socket: disconnect a client that cannot consume its bounded outbound queue, then let it recover through history synchronization.

05 / MESSAGE FLOW

Acknowledge only after durable acceptance

  1. Authenticate and authorize. The gateway validates the session; the chat API confirms cached conversation membership.
  2. Deduplicate the command. A unique (sender_id, client_message_id) identifies retries.
  3. Append to Kafka. Publish using conversation_id as the key and wait for all in-sync replicas to acknowledge.
  4. Acknowledge the sender. Return the durable Kafka partition offset as a stable conversation ordering token.
  5. Persist and fan out. A consumer writes Cassandra, looks up active recipient sessions, and forwards the message.
  6. Track delivery. Device acknowledgements update a compact receipt cursor and notify the sender asynchronously.

The sender may render its message optimistically before server acknowledgement. If the socket drops, it resends the same client message ID. The service returns the previous result instead of creating a duplicate.

06 / ORDERING

Order within a conversation, not globally

All commands for one conversation use the same Kafka partition. Kafka's partition leader serializes appends and assigns increasing offsets. Store the offset with each message as its sequence. Other conversations share the partition, so their offsets create harmless gaps in any one conversation.

What is guaranteed

Every participant eventually displays the same committed order for messages in a conversation.

What is not guaranteed

A message composed first on one phone may arrive after a message sent later from another phone. Server acceptance defines order.

Edits, deletions, reactions, and membership events use the same conversation partition, preserving their order relative to messages. Clients buffer a short out-of-order gap and fetch missing sequence ranges rather than waiting forever.

Kafka offsets are internal. Expose an opaque sequence token rather than coupling public clients to topic and partition names. This allows repartitioning through a migration.
07 / DATA MODEL

Store messages for sequential reads

Cassandra partitions by conversation and time bucket—such as month or week—to prevent a long-lived group from creating an unbounded partition. Rows sort by sequence for efficient pagination. The client uses an opaque cursor containing bucket and sequence.

Clients upload attachments directly to S3 with presigned multipart URLs. A message references an attachment only after scanning and metadata validation succeed. Downloads use short-lived signed CDN URLs rather than proxying bytes through chat servers.

08 / FAN-OUT

Scale fan-out by active devices

After persistence, the fan-out service reads the conversation's membership version and finds online devices in Redis. It batches one RPC per destination gateway; each gateway writes to its local sockets. Offline users do not receive a durable copy in a separate inbox—the conversation log is already their source of truth.

Small groups

Push immediately to every connected member. The low fan-out gives the best latency and straightforward receipts.

Very large groups

Gateways subscribe only while they host interested users. Batch delivery by gateway and let clients fetch missed history.

A celebrity channel with millions of members should use a pub/sub channel design rather than per-member chat fan-out. Product limits on group size protect both latency and storage hot partitions.

09 / RECOVERY

Make reconnection a normal path

Each device maintains a durable cursor per conversation and a global synchronization cursor for conversation-list changes. On reconnect, the client sends its latest cursors and fetches all committed events after them. 

GET /v1/sync?cursor=eyJ2ZXJzaW9uIjo...

{
  "events": [
    { "type": "message", "conversation_id": "conv_842", "sequence": 9281042 },
    { "type": "read_cursor", "conversation_id": "conv_17", "sequence": 5519 }
  ],
  "next_cursor": "eyJ2ZXJzaW9uIjo..."
}

Push notifications through APNs and FCM are hints, not delivery records. They may be delayed, collapsed, or dropped. Opening the app always invokes sync. Keep notification payloads minimal to avoid exposing message content on locked devices.

Compact receipts

Do not store one receipt row for every user and message. For each user-device pair, store the highest contiguous delivered and read sequence per conversation. A cursor implies receipt for every prior message and compresses state dramatically.

10 / EPHEMERAL STATE

Keep presence approximate

Gateways refresh Redis session keys with a 60-second TTL. A user is online when at least one device lease is alive. Disconnect events remove leases promptly, while TTL handles crashes and network loss.

  • Presence: coalesce updates and show coarse states such as online or last seen.
  • Typing: publish ephemeral events with a short TTL; never persist them to message history.
  • Last seen: write asynchronously when the final device lease expires.
  • Privacy: apply visibility rules before publishing any presence state.

Exact global presence would require constant cross-region coordination and still become stale when networks fail. Approximate presence gives a better availability and cost trade-off.

11 / MULTI-REGION

Give each conversation a home region

Clients connect to the nearest region, but every conversation has a home region selected by consistent hashing. The local chat API forwards sends to that home, where one Kafka partition establishes order. Recipient events return over regional backbone streams.

Why a home region?

It avoids conflicting multi-leader orders. One extra regional hop is preferable to permanent message-order disagreement.

Home-region outage

Pause sends briefly, fence the old leader, promote a replicated log in the failover region, then resume from its committed offset.

Replicate message storage across regions asynchronously for history reads and disaster recovery. Presence remains region-local and is aggregated approximately. Do not acknowledge a cross-region message until its home-region Kafka quorum accepts it.

Production signals

  • Connected sockets, reconnect rate, and gateway queue depth
  • Send-to-accept, accept-to-persist, and persist-to-deliver latency
  • Kafka producer failures, partition skew, and consumer lag
  • Cassandra write latency and oversized conversation partitions
  • Duplicate command rate and sequence-gap recovery
  • Push notification delay and offline-sync duration

Security and privacy

Encrypt traffic with TLS and data with managed keys, authorize every conversation access, rate-limit sends and membership changes, and scan attachments. End-to-end encryption requires client-managed conversation keys, device verification, and encrypted history backups; it also removes server-side search and moderation of message bodies, so it must be an explicit product decision.

Final design summary

Go WebSocket gateways maintain real-time connections while Kafka durably orders every conversation. Cassandra stores paginated history, PostgreSQL protects membership, Redis tracks ephemeral sessions, and S3 handles attachments. Idempotent client message IDs make retries safe; cursor-based sync makes disconnection ordinary. Conversation home regions trade one network hop for deterministic order, while asynchronous fan-out keeps delivery scalable.
