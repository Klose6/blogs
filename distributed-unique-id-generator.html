Designing a Distributed Unique ID Generator

Snowflake IDs Coordination Clock safety 11 min read

How can thousands of servers create billions of IDs without collisions, a database round trip, or a central bottleneck? We will encode time, generator identity, and a local sequence into one sortable 64-bit number.

01 / SCOPE

Define what “unique” means

The service generates identifiers for orders, posts, messages, and other records before they reach storage. IDs must never collide across machines or regions, and generating one must not require a synchronous call to a central database.

Functional

  • Globally unique within the system's lifetime
  • Roughly sortable by creation time
  • Representable as a signed 64-bit integer
  • Decodable for operational debugging

Non-functional

  • At least 10 million IDs per second globally
  • Local generation below 1 ms
  • No central dependency on the hot path
  • Safe through restarts and clock adjustments
Not a security token: sortable IDs reveal ordering and approximate creation time. Use a separate random public token when identifiers must be unguessable.
02 / ALGORITHMS

Choose the right ID shape

ApproachHow it worksTrade-off
Database sequence One transactional counter returns the next integer Simple and ordered, but centralizes every write
Range allocation Workers reserve blocks such as 1–10,000 Fast locally, but restart gaps and coordination remain
UUIDv4 122 random bits make collisions astronomically unlikely No coordination, but 128 bits and poor index locality
UUIDv7 / ULID Timestamp prefix plus random bits Sortable and decentralized, but still 128 bits
Snowflake Timestamp + worker ID + per-millisecond sequence Compact and fast, but requires clock and worker safety

Use UUIDv7 when 128-bit IDs are acceptable and operational simplicity matters most. This design chooses a Snowflake-style ID because the requirement is a compact, time-sortable 64-bit integer generated at very high throughput.

12 sequence bits allow about 4.1M IDs/s.

id = ((now_ms - custom_epoch) << 22)
   | (worker_id << 12)
   | sequence

Reserve the highest bit so IDs remain positive in signed databases. A custom epoch such as 2026-01-01T00:00:00Z extends useful lifetime. The ID is roughly—not globally strictly—ordered: two workers can generate nearby IDs in a different arrival order.

04 / HIGH LEVEL

Keep coordination off the hot path

etcd and chrony support the generator from side paths; neither adds a network call to normal in-process ID generation.

Embed the generator as a Go library in each application process. At startup, a process acquires a unique worker lease from etcd. After that, ID generation uses only the local clock, worker ID, and sequence counter. This removes a network hop and central bottleneck.

A standalone gRPC generator service is useful for languages without a trusted library or when policy must be centralized, but it adds latency and becomes another availability dependency. Prefer the library for internal services and expose gRPC only as a compatibility layer.

05 / HOT PATH

Generate with a small critical section

  1. Read the clock. Get the current Unix time in milliseconds and subtract the custom epoch.
  2. Compare timestamps. If time advanced, reset the sequence to zero. If it is unchanged, increment the sequence.
  3. Handle exhaustion. After sequence 4,095 in one millisecond, wait until the next millisecond rather than wrapping.
  4. Assemble the ID. Shift each field into place and combine them with bitwise OR. 
func NextID() (uint64, error) {
    lock()
    defer unlock()

    now := clock.NowMillis()
    if now < lastMillis {
        return 0, ErrClockMovedBackward
    }
    if now == lastMillis {
        sequence = (sequence + 1) & 0xFFF
        if sequence == 0 {
            now = waitForNextMillis(lastMillis)
        }
    } else {
        sequence = 0
    }
    lastMillis = now
    return ((now - epoch) << 22) |
           (workerID << 12) |
           sequence, nil
}

A mutex is usually sufficient because the critical section is tiny. Benchmark before adding lock-free complexity. Generate IDs in small local batches only if profiling shows contention.

06 / CLOCK SAFETY

Never generate into the past

If a worker's wall clock moves backward, it may reuse a previous timestamp and sequence, producing a collision. This can happen after an NTP step, VM migration, or manual clock change.

Small rollback

For a rollback of at most 5 ms, pause until physical time catches up. The request sees a small latency spike but uniqueness holds.

Large rollback

Stop generation, fail readiness, and alert. Restart only after the clock passes the last emitted timestamp or acquire a new worker ID that has not generated in the conflicting interval.

Run chrony on every host and configure it to slew normal corrections rather than step the clock after startup. Persist the last emitted timestamp periodically and check it during process startup so a restart cannot hide a rollback.

Do not use monotonic time in the ID: monotonic clocks are excellent for measuring duration but have no stable epoch across restarts. Use wall time for encoding and monotonic time for waits.
07 / WORKER IDENTITY

Lease, do not hard-code, worker IDs

Duplicate worker IDs are more dangerous than temporary downtime: two generators with the same millisecond and sequence will collide. Each process therefore creates an ephemeral etcd lease for one of the 1,024 worker slots. 

/id-workers/042 = {
  "instance": "orders-7f59c",
  "region": "us-east-1",
  "started_at": "2026-09-13T23:40:00Z"
}
lease_ttl: 30 seconds
  • Acquire the worker key using an etcd compare-and-swap transaction.
  • Renew the lease every 10 seconds and stop generation if ownership is uncertain.
  • Fence each lease with its etcd revision so a stale process cannot resume.
  • Delay reuse of an expired worker ID beyond the maximum clock-skew window.

Kubernetes StatefulSet ordinals can supply stable IDs, but only when a single cluster owns the complete namespace. etcd leases are safer across multiple deployments and handle abandoned slots automatically.

08 / MULTI-REGION

Partition worker space by region

Avoid cross-region etcd consensus by dividing the 10 worker bits into 3 region bits and 7 process bits. Each of eight regions runs its own etcd cluster and can assign 128 local workers independently.

Region codes come from deployment configuration and must never be reused by two active regions. If eight regions or 128 workers per region are insufficient, reallocate bits based on measured lifetime and throughput needs—or adopt UUIDv7 instead of forcing too many constraints into 64 bits.

09 / IMPLEMENTATION

Recommended technology stack

ResponsibilityToolWhy it fits
ID generation Go library Fast local bit operations, small critical section, easy embedding
Worker leases etcd Linearizable transactions, TTL leases, and watch notifications
Clock synchronization chrony Monitors drift and slews corrections safely
Compatibility API gRPC Efficient batched IDs for clients that cannot embed the library
Deployment Kubernetes Readiness controls stop unsafe generators from receiving traffic
Monitoring Prometheus + Grafana Tracks drift, throughput, sequence pressure, and lease health

On AWS, run the Go workloads on EKS and operate a small etcd cluster per region across three availability zones. DynamoDB conditional writes plus TTL can allocate worker IDs, but TTL deletion is not immediate; etcd's lease semantics are a cleaner fit for ownership.

10 / PRODUCTION

Monitor the assumptions behind uniqueness

Critical signals

  • Clock offset and backward-clock events
  • Worker lease renewal failures
  • Duplicate worker ownership attempts
  • Sequence exhaustion and generation latency

Safe rollout checks

  • Custom epoch and bit layout match everywhere
  • Every region has a unique configured code
  • Database columns use signed 64-bit integers
  • JavaScript APIs serialize IDs as strings

JavaScript numbers cannot exactly represent every 64-bit integer. Return IDs as decimal strings in JSON and parse them with BigInt when arithmetic is required. Database primary keys may remain BIGINT.

Final design summary

A Snowflake-style layout creates compact, roughly time-ordered IDs from a timestamp, worker identity, and local sequence. A Go library keeps generation off the network path, etcd safely leases worker IDs, and chrony limits clock risk. Region bits remove cross-region coordination. The design favors availability and throughput while explicitly stopping whenever uniqueness cannot be guaranteed.
